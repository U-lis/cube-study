# 코너 3-Style UBL 조회 + 퀴즈 - Specification

## Overview

3BLD(눈가리고 큐브 맞추기)를 M2OP 메서드로 수련 중인 사용자가 **코너 3-style을 학습**하기 위한 도구다.

현재 3-style 알고리즘 378개는 PDF로 보유하고 있으나, 연습 도중 인덱스를 찾아 스크롤로 뒤지는 것이 불가능에 가깝다. 이 앱의 1차 목적은 **스티커 2글자를 입력하면 어떤 기준공식(anchor) 케이스인지와 실제 공식을 즉시 보여주는 것**이다.

2차 목적은 **큐브 없이 하는 연습**이다. 케이스를 문제로 제시하고 사용자가 공식을 입력하면 정오를 판정한다. 판정은 문자열 비교가 아니라 큐브 시뮬레이터로 수행한다 — 같은 3-cycle을 만드는 알고리즘은 여러 개 존재하므로(HANDOFF.md:238), 문자열 비교는 올바른 풀이를 대량 오답 처리한다.

데이터는 이미 완성·검증되어 있다(`.dc_workspace/handoff/3style_ubl_data.v2.json`, 378케이스). 이 앱은 데이터를 **표시**할 뿐 알고리즘을 계산하지 않는다.

**Target Version**: 0.1.0
**Buffer / PieceType**: UBL / corner (단일 데이터셋)

### 사용자 맥락

| 항목 | 현황 |
|---|---|
| 현재 메서드 | 코너 OP + 엣지 M2, 버퍼 UBL |
| 3BLD 평균 | 약 6분, 성공률 약 50% |
| 3-style 진행도 | 학습 시작 전 (개념 이해 단계) |
| 주 사용 시나리오 | 연습 중 모바일에서 **한 손으로** 조회 |

학습 초기이므로 **setup 모드가 기본값**이다. 기준공식 10개만 외우고 셋업으로 378개를 처리하는 단계이기 때문이다(HANDOFF.md:56).

## Functional Requirements

### 데이터 레이어

- [ ] FR-1: 데이터 로더를 `{pieceType, buffer}` 키로 분리
  - 시그니처: `loadDataset({ pieceType: 'corner', buffer: 'UBL' }): Promise<Dataset>`
  - 내부에서 동적 `import()`로 데이터셋별 청크 분리
  - 0.1.0은 `corner/UBL` 하나만 구현하되, UFR·엣지 추가 시 로더 시그니처가 바뀌지 않아야 한다
  - 데이터 원본은 `src/lib/data/` 아래에 두어 Vite가 번들·해싱하도록 한다 (`static/` 아님)

- [ ] FR-2: 타입 정의
  - `Sticker`, `Cubie`, `Face`, `CaseCode`, `Anchor`, `CaseEntry`, `Dataset` 등 TypeScript 타입을 데이터 스키마(schemaVersion 2)에 맞춰 정의
  - `direct.strict` / `setup.strict` / `sameAlg` / `inverseTrick` 필드 포함

### 조회 (F1) — 최우선

- [ ] FR-3: 케이스 입력 — 키보드 전용
  - **입력은 키보드로만 받는다.** 온스크린 스티커 패드(21~24버튼)를 두지 않는다
    - 근거 1: 21개 버튼은 화면을 크게 점유해 FR-4의 sticky 결과 영역과 공간을 두고 경쟁한다
    - 근거 2: 사용자는 이미 OP + M2로 3BLD를 수행 중이라 Speffz 레터가 손에 익어 있다. 버튼의 주 효용인 탐색 보조가 필요 없다
  - 2글자가 채워지면 **즉시** 결과 표시 (별도 확인 버튼 없음)
  - 대소문자 무시
  - **Speffz 범위(A~X) 밖 문자는 받지 않는다.** 입력을 무시하고 입력 필드 배경을 잠시 빨강으로 전환했다 되돌려 "잘못된 입력"만 알린다. 별도 메시지를 띄우지 않는다
    - 한글 IME가 켜진 상태의 자음, 숫자, 기호가 모두 이 규칙 하나로 처리된다. IME 조합 이벤트를 따로 다루지 않는다
  - **모바일 OS 키보드 대응**:
    - `autocapitalize="off"`, `autocorrect="off"`, `autocomplete="off"`, `spellcheck="false"` — 자동 대문자·자동수정 간섭 차단
    - 입력 필드는 화면 상단에 고정해 OS 키보드가 올라와도 결과 영역이 가려지지 않게 한다
  - 데스크탑에서는 물리 키보드로 그대로 동작한다

- [ ] FR-4: 입력 상태별 표시 — 결과 유지(sticky)
  - **마지막으로 조회에 성공한 결과를 화면에 유지한다.** 글자를 지워 2글자 미만이 되어도 결과를 지우지 않는다
  - 새 2글자가 완성되면 그 시점에 결과를 교체한다
  - 현재 입력과 표시 중인 결과가 다를 때는 결과를 흐리게(회색) 처리해 "지금 입력과 다름"을 알린다
  - 1글자 입력 시 후보 목록(해당 문자로 시작하는 18개, 문자 무관 항상 18개)을 표시하되, **후보 목록이 결과를 밀어내지 않는 별도 영역**에 띄워 레이아웃 점프를 방지한다
  - 후보를 탭하면 해당 케이스로 이동
  - 근거: 오타로 한 글자를 지웠을 때 결과가 사라졌다 다시 나타나면 화면이 크게 두 번 바뀌어 산만하다

- [ ] FR-5: 무효 입력 판별 및 사유 표시
  - 전체 24×24 = 576조합 중 유효 378, 무효 198
  - 무효 사유를 구분해 표시한다:

  | 유형 | 조합 수 | 표시 문구 예 |
  |---|---|---|
  | 버퍼 스티커 포함 | 135 | "A는 버퍼(UBL) 스티커라 케이스에 등장하지 않습니다" |
  | 같은 글자 반복 | 21 | "같은 스티커 두 개는 3-cycle이 아닙니다" |
  | 서로 다르지만 동일 큐비 | 42 | "B와 N은 같은 큐비(UBR)라 3-cycle이 아닙니다" |

  - 무효 판정 시에도 FR-4에 따라 직전 유효 결과는 화면에 남는다

- [ ] FR-6: 조회 결과 — 공통 영역
  - 케이스 코드를 크게, 가운데 정렬
  - 두 타깃 위치를 `L = DFL의 F면` 형식으로 표시 (큐비 + 면)
  - 역 케이스 링크 (`LB` ↔ `BL`). 탭하면 해당 케이스로 이동
  - 알고리즘은 **왼쪽 정렬** (가운데 정렬 시 읽기 혼란 — 기존 PDF에서 사용자가 명시 요청한 관례)

- [ ] FR-7: setup 모드 표시 (기본 모드)
  - **기준공식 이름을 결과 화면에서 가장 크게 노출** — "어떤 베이스 공식 케이스인가"가 첫 질문이다
  - 셋업 무브 `S`
  - 기준공식의 알고리즘
  - 기준공식의 입구 2자리 (`입구1: L = DFL의 F면`)
  - 최종 알고리즘 (상쇄 적용된 `setup.alg`)
  - `anchor`가 `(직접)`인 6케이스(`CU CW UC UW WC WU`)는 기준공식이 없음을 배지로 명시. 이 케이스들의 `setup.alg`는 `direct.alg`와도 다른 제3의 13수 알고리즘이므로 혼동 없이 표시한다

- [ ] FR-8: direct 모드 표시
  - 전용 최적 알고리즘과 무브 수
  - `type`이 `pure`면 `[A, B]` 구조, `conj`면 `[S: [A, B]]` 구조로 표시
  - `A`는 "인서트", `B`는 "교환"으로 라벨링

- [ ] FR-9: direct ↔ setup 토글
  - 두 모드 전환이 매끄러워야 한다
  - `sameAlg`가 `true`인 29케이스는 두 모드의 **최종 무브 열이 동일**하다. 단 분해 방식까지 같은 것은 아니다 (예: `FS`는 direct가 `[F : [U2, R' D2 R]]`, setup이 `[F U2 : SC]`로 셋업 무브부터 다르다)
  - **배지는 compact 모드에서만 표시한다.** strict 모드에서는 괄호 표기가 달라 두 모드가 이미 구분되므로 배지가 불필요하다
  - 배지 문구는 "최종 무브 열이 같습니다"로 한다. "두 방식의 공식이 같습니다"는 분해가 다른 25건에서 부정확하다

- [ ] FR-10: strict ↔ compact 토글
  - **strict**: 상쇄를 적용하지 않은 구조형. 파트 경계를 괄호 표기로 구분한다. 데이터의 `strict.alg`를 쓴다. 모드별 표기가 다르다:

  | 모드 | type / 조건 | 표기 | 예 |
  |---|---|---|---|
  | direct | `pure` (S 없음) | `[A , B]` | `[R D2 R' , U]` |
  | direct | `conj` (S 있음) | `[S : [A , B]]` | `[L : [R' D2 R , U2]]` |
  | setup | 셋업 있음 | `[S : 기준공식이름]` | `[F U2 : SC]` |
  | setup | 셋업 없음 (4건) | 기준공식 이름만 | `LB` |
  | setup | `(직접)` (6건) | 괄호 없이 알고리즘 | — |

  - setup 모드의 strict는 기준공식을 **이름으로** 표기한다. 기준공식의 알고리즘 자체는 FR-7에 따라 별도 영역에 함께 보여주므로 중복 나열하지 않는다
  - **compact**: 상쇄를 적용한 실행형. 괄호 없이 단색 평문. 데이터의 `alg`를 쓴다. 괄호 유무가 두 모드를 구분하는 1차 신호가 된다
  - compact는 상쇄로 파트 경계가 물리적으로 소실되므로 파트 구분 표시가 **불가능**하다. 이는 설계 선택이 아니라 데이터상 필연이다
  - `strict.cancels`가 0인 케이스(direct 210건)는 두 표현의 무브 열이 동일하다. 이때도 strict는 구조 표기를, compact는 평문을 보인다
  - 색 사용은 A(인서트)·B(교환) 두 가지로 한정하고 `S`는 기본 텍스트 색으로 둔다. 구조 인식의 주된 수단은 색이 아니라 괄호 표기다


### 기준공식 브라우저 (F2)

- [ ] FR-11: 기준공식 10개 목록
  - 담당 케이스 수 내림차순 정렬: LB 100 → TU 83 → SC 60 → NG 46 → UN 35 → WM 18 → NU 12 → KD 9 → UB 8 → KS 1
  - 각 항목에 알고리즘, 무브 수, 입구 2자리, 담당 케이스 수 표시
  - 담당 케이스 수는 숫자만 적는다. 백분율·누적 커버리지·학습 우선순위 안내를 붙이지 않는다 (NFR-9)

- [ ] FR-12: 기준공식별 케이스 목록
  - 기준을 탭하면 그 기준을 쓰는 케이스 목록으로 이동
  - 셋업이 짧은 것부터 정렬 (쉬운 것 먼저 — 기존 PDF 관례)
  - `(직접)` 6케이스는 별도 그룹으로 표시

### 큐브 시뮬레이터 (F4)

- [ ] FR-13: 시뮬레이터 이식
  - **신규 구현하지 않는다.** `.dc_workspace/handoff/sim/cube-sim.js`(ES 모듈, 의존성 없음)와 `cube_perms.json`을 `src/lib/` 아래로 이식하고 TypeScript 타입을 입힌다
  - 상태 모델은 **스티커 치환** 방식이다: `{ 위치: 그_위치에_있는_원래_스티커 }`. 코너 24스티커(`A`~`X`)와 엣지 24스티커(`a`~`x`)를 각각 추적한다. Speffz 레터링과 직결되어 케이스 코드 판정이 자연스럽다
  - 무브 적용 규약: `newState[pos] = oldState[table[pos]]`. `cube_perms.json`의 테이블에는 **역치환이 미리 적용**되어 있다. Python 원본(`bld_sim.py`)은 반대 규약이므로 그쪽을 참고해 옮기면 결과가 어긋난다
  - 지원 무브는 **27종**: `U L F R B D` + **`M E S` 슬라이스** × (정방향/`'`/`2`). 코너 3-style은 18종만 쓰지만 슬라이스가 이미 지원되므로 **M2 엣지 확장 시 시뮬레이터를 고칠 필요가 없다**
  - 엣지를 추적하는 이유는 **엣지 무영향 판정** 때문이다. 엣지 먼저 푸는 표준 순서에서 코너 알고리즘이 엣지를 건드리면 이미 푼 엣지가 깨진다(HANDOFF.md:105)

- [ ] FR-14: 시뮬레이터 API
  - `identifyCase(alg)` — 알고리즘이 어떤 케이스를 푸는지 역판정. 케이스 코드 또는 3-cycle이 아니면 `null`. **퀴즈 채점의 핵심**
  - `isEdgeNeutral(alg)` — 엣지 무영향 여부. 부분 정답 판정에 사용
  - `affectedCubies(state, kind)` — 영향받은 큐비 집합. 오염된 엣지 표시에 사용
  - `invertAlg` / `cancelMoves` / `moveCount` — 표기 유틸. 시뮬레이터 없이도 사용 가능
  - 유효하지 않은 무브 토큰은 오류를 던진다 (`Unknown move: {tok}`)

- [ ] FR-15: 빌드 타임 데이터 검증
  - `handoff/sim/test_sim.mjs`(원본 1134건)와 `test_v2.mjs`(v2 파생 필드 5292건)를 프로젝트 테스트로 편입한다
  - 두 스크립트는 현재 상태에서 **전부 통과**함을 확인했다. 데이터나 시뮬레이터를 건드리는 변경 후에는 반드시 재실행한다

### 퀴즈 (F3)

- [ ] FR-16: 출제
  - 378케이스 중 무작위로 케이스 코드를 제시
  - 정답을 보기 전까지 알고리즘을 숨긴다
  - 0.1.0은 학습 상태를 저장하지 않으므로 출제 이력은 세션 메모리에만 유지한다

- [ ] FR-17: 공식 입력 — 버튼 방식
  - `U L F R B D` 6면 × (정방향 / `'` / `2`) 18개 버튼으로 입력
  - 조회(FR-3)와 달리 **여기서는 버튼을 쓴다.** `R'`를 키보드로 입력하려면 프라임 문자를 따로 쳐야 하고, 모바일 OS 키보드에서 `'`는 보통 2단계 깊이에 있어 연속 입력이 끊긴다
  - 되돌리기(마지막 무브 삭제)와 전체 지우기 제공
  - 입력된 무브 열을 고정폭으로 실시간 표시
  - 모바일 한 손 조작을 고려해 버튼을 하단에 배치

- [ ] FR-18: 판정
  - `identifyCase(입력알고리즘)`의 반환값을 출제된 케이스 코드와 비교한다
  - 데이터에 없는 변형 알고리즘이라도 같은 효과면 **정답 처리**한다
  - 판정 결과를 다음과 같이 구분한다:

  | 결과 | 조건 | 피드백 |
  |---|---|---|
  | 정답 | 코너 3-cycle 일치 + 엣지 무영향 | 정답 표시 |
  | 부분 정답 | 코너 3-cycle 일치 + **엣지 오염** | "코너는 맞지만 엣지를 건드립니다" + 영향받은 엣지 표시 |
  | 오답(방향) | 3개 큐비 위치는 맞으나 방향(twist) 불일치 | 방향이 틀렸음을 표시 |
  | 오답 | 그 외 | 오답 표시 |

## Non-Functional Requirements

- [ ] NFR-1: 조회 즉각성 — 2글자 입력 완료에서 결과 표시까지 **100ms 이내**. 연습 중 한 손 조회가 주 시나리오이므로 체감 지연이 곧 실패다.
- [ ] NFR-2: 콜드스타트 — 앱 실행에서 입력 가능 상태까지 **1초 이내**.
- [ ] NFR-3: 고정폭 글꼴 — 큐브 표기는 고정폭 필수. `R`과 `R'`이 명확히 구분되어야 한다. 오프라인이므로 폰트를 **번들에 포함**하고 CDN을 쓰지 않는다. 필요 글리프만 서브셋한다.
- [ ] NFR-4: ASCII 프라임 — 프라임 기호는 반드시 ASCII `'`(U+0027). 타이포그래피 따옴표로 자동 변환되어서는 안 된다. 마크다운 렌더러를 쓰지 않고, 알고리즘 문자열은 텍스트 보간으로만 출력하며 `{@html}`을 쓰지 않는다. CSS `font-variant-ligatures: none`을 적용한다. 복사해서 붙여넣었을 때 ASCII여야 한다.
- [ ] NFR-5: 무브 줄바꿈 — 무브 사이 공백을 유지하되 줄바꿈이 무브 중간에서 끊기지 않아야 한다. 알고리즘을 토큰 배열로 쪼개 각 무브를 `white-space: nowrap` 단위로 감싸고 컨테이너를 flex-wrap 한다.
- [ ] NFR-6: 확장성 — 데이터 로더가 `{pieceType, buffer}`로 분리되어 UFR 코너·엣지 3-style·M2/OP 참조표를 데이터 추가만으로 붙일 수 있어야 한다.
- [ ] NFR-7: UI 언어 — 한국어를 기본으로 하되, 큐브 표기(`R U R' U'`)와 케이스 코드는 영문 그대로 둔다.
- [ ] NFR-8: 오프라인 — 설치 후 네트워크가 완전히 끊긴 상태에서 모든 기능(조회·브라우저·퀴즈)이 동작해야 한다.
- [ ] NFR-9: **UI 톤 — dry한 정보 앱.** 필요한 것만 빠르고 깔끔하게 준다. 다음을 넣지 않는다:
  - 백분율·커버리지·진도율을 앞세운 동기부여 문구 ("상위 3개로 64% 커버!", "이만큼 익히셨어요")
  - 격려·칭찬·권유 ("잘하고 있어요", "이것부터 외워보세요")
  - 배지·연속 기록·축하 연출 등 게이미피케이션
  - 사용자가 이미 아는 것을 반복 설명하는 안내

  표시해도 되는 것은 **사실**이다. 담당 케이스 수(`100`), 무브 수(`8수`), 판정 결과, 데이터에서 직접 오는 상태(`(직접)`, "최종 무브 열이 같습니다"). 사실과 코칭의 경계가 애매하면 빼는 쪽을 택한다.

## Constraints

- **기술 스택 고정**: SvelteKit 2 + TypeScript + `adapter-static` + `@vite-pwa/sveltekit`. 정적 빌드 산출물을 기존 Ubuntu 서버(nginx + acme.sh HTTPS)에 배포한다. 서버 런타임을 두지 않는다.
- **데이터 재계산 금지**: `3style_ubl_data.v2.json`의 알고리즘을 재계산하거나 "더 짧은 것"으로 교체하지 않는다. 모든 알고리즘은 큐브 시뮬레이터로 3중 검증(메모 방향 / 코너 해결 / 엣지 무영향)을 통과했으며, 길이만 보고 최적화하면 엣지 무영향 조건이 깨진다.
- **런타임 파생 금지**: `alg`를 `A`/`B`/`S`에서 상쇄로 재생성하거나 `setup.alg`를 anchor에서 재조립하지 않는다. 검증된 값을 클라이언트 코드로 다시 만드는 순간 그 검증이 보증하는 것이 없어진다. 저장된 값을 그대로 읽어 쓴다. (시뮬레이터는 **판정 목적**으로만 쓰며 표시할 알고리즘을 생성하지 않는다.)
- **시뮬레이터 신규 구현 금지**: `handoff/sim/cube-sim.js`는 378케이스 전수 검증을 통과한 참조 구현이다. 이식하고 타입만 입히며, 상태 모델이나 무브 적용 규약을 바꾸지 않는다.
- **역트릭 런타임 적용 금지**: 역 케이스는 `inverse` 필드로 참조한다. 뒤집기를 직접 구현하지 않는다.
- **데이터 무결성**: 앱은 378케이스를 모두 조회할 수 있어야 하며, 데이터의 어떤 케이스도 누락하거나 병합하지 않는다.
