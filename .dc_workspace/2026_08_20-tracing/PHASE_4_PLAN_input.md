# Phase 4 — 입력과 결과 (input)

**담당**: FR-TR-10~13, 18, 20, 23(표시), 24, 25; NFR-TR-5
**의존**: Phase 3 완료
**병렬 불가**: `/trace/+page.svelte` 를 계속 고친다

## 목표

이 페이즈가 끝나면:
- 24글자 온스크린 패드와 하드웨어 키보드로 타깃 열을 입력할 수 있다
- 입력 구획이 **타깃 열 / 비틀림** 둘로 나뉘고, 관례 A 에서는 비틀림 칸이 비활성이다
- 채점 결과가 나온다 — 정답 / 첫 어긋난 지점 / 불필요한 끊기 / 패리티 / 정답 예시 / 두 관례의 타깃 수
- 소요 시간이 기록되고 직전 기록들과 함께 보인다

## 선행 조건

- Phase 3 완료. `/trace` 가 세션을 돌린다

## 수정·생성할 파일

### `src/lib/ui/StickerPad.svelte` (신규)

24글자 온스크린 패드. `MoveKeypad.svelte` 와 같은 발상이다 — 모바일 키보드에서 연속 입력이 끊기기 때문에
버튼을 쓴다 (`MoveKeypad.svelte:1-5`). 0.1.0 SPEC 이 "온스크린 스티커 입력 패드 | 0.2.0 이후 재검토" 로
미뤄둔 항목이 여기서 돌아온다 (SPEC.md:242 인용, FR-TR-18).

| props | 타입 | 설명 |
|---|---|---|
| `letters` | `string[]` | 24글자. 코너면 `CORNER_LETTERS`, 엣지면 `EDGE_LETTERS` (`speffz.ts:51-52`) |
| `value` | `$bindable<string[]>` | 입력된 문자 열 |
| `disabled` | `boolean` | |
| `max` | `number` | 상한 (폭주 방지. `MoveKeypad.svelte:9` 의 `MAX_MOVES` 와 같은 취지) |

- 코너는 **대문자**, 엣지는 **소문자** 로 표시한다 (`CORNER_INDEX`/`EDGE_INDEX` 표기를 그대로 따른다)
- 삭제(한 글자)·전체 지우기 버튼
- **버튼 개수·크기가 SSR/CSR 에서 같다.** `{#if}` 로 버튼을 빼지 않는다 (GLOBAL AD-14)
- 터치 타깃 44px 이상
- 버퍼 스티커 버튼은 **표시하되 눌러도 들어가지 않는다** — 24글자 배치를 흐트러뜨리지 않으면서
  "버퍼는 타깃이 아니다" 를 눈으로 알린다 (HANDOFF §4.1). 비활성 표시를 색만으로 하지 않는다
- 관례 B 의 비틀림 칸에서는 **버퍼 문자도 입력 가능** 해야 한다 — 버퍼가 비틀린 채 남는 경우가 코너
  80.9% 다 (FR-TR-24). 즉 버퍼 차단은 **타깃 구획에만** 건다

### 하드웨어 키보드 (FR-TR-18)

- 코너 세션: `A`~`X` (대문자 입력, `Shift` 없이 눌러도 받아준다 — 세션이 조각 종류를 안다)
- 엣지 세션: `a`~`x`
- `Backspace` 삭제, `Escape` 전체 지우기, `Enter` 제출
- 포커스가 입력 구획에 있을 때만 받는다. 전역 키 훅으로 다른 화면을 방해하지 않는다

### `src/routes/trace/+page.svelte` (수정)

입력 구획 둘:

| 구획 | 내용 | 관례 A | 관례 B |
|---|---|---|---|
| 타깃 열 | 순서가 의미 있다 | 활성 | 활성 |
| 비틀림 | **집합** 으로 본다 (순서 채점 없음) | **비활성** | 활성 |

실전이 letter 열과 twist 를 따로 담는 것과 같다 (FR-TR-18). 관례 A 에서는 비틀림이 전부 타깃 열에
들어가므로 칸을 비활성한다 — 숨기지 않는다 (레이아웃 점프 방지).

제출 → `gradeMemo(state, { targets, twists }, opts)` → `verdictText` 로 표시.

결과 화면에 담는 것:

| 항목 | 출처 | FR |
|---|---|---|
| 판정 문구 | `verdictText` | FR-TR-11, 12 |
| 첫 어긋난 지점 | `wrong-at.index` (표시는 1부터) | FR-TR-11 |
| 정답 예시 하나 + "정답은 여럿입니다" | `trace()` 결과 + 안내 문구 | FR-TR-20, 10 |
| 패리티 | `TraceResult.parity` — 코너 타깃 홀수 | FR-TR-13 |
| 두 관례의 타깃 수 | `conventionCompare` | FR-TR-24 |
| 이번 시간 + 직전 기록들 | `tracing.records` | FR-TR-23 |

패리티 설명은 한 줄로 사실만 적는다 — "코너 타깃이 홀수입니다 (패리티)". 처리 알고리즘 안내는 범위 밖이다
(#17·#18 참조표가 생긴 뒤). 근거는 HANDOFF §4.6 이다.

관례 B 결과에서 **버퍼 비틀림은 따로 표시** 한다. "왜 이게 목록에 있는가" 가 반드시 나오는 질문이고,
방향 합 보존 때문이라는 사실이 학습에 직결된다 (GLOBAL AD-8).

채점 후 기록을 저장한다 — `{ at, ms, pieceKind, buffer, mode, targetCount, correct }` (Phase 2 의 스키마).

**정답 예시를 사용자의 입력과 문자열 비교해 "틀렸다" 고 말하지 않는다.** 유효한 메모가 평균 11가지다
(FR-TR-10). 예시는 예시일 뿐이다.

## 이 페이즈에서 조심할 것

| 위험 | 대응 |
|---|---|
| 채점을 문자열 비교로 함 | 화면은 `gradeMemo` 결과만 쓴다. 정답 예시와 비교하는 코드가 있으면 안 된다 |
| 관례 A 에서 비틀림 칸을 `{#if}` 로 제거 | 레이아웃이 점프한다. `disabled` 로 처리 |
| 비틀림 구획에서 버퍼 문자를 막음 | 버퍼가 80.9% 로 비틀린 채 남는다. 막으면 관례 B 훈련이 성립하지 않는다 |
| 비틀림 순서를 채점 | 집합으로 본다 (FR-TR-18) |
| 전역 키 훅으로 다른 화면을 방해 | 입력 구획에 포커스가 있을 때만 |
| 입력 길이 폭주 | `max` 상한 (`MoveKeypad.svelte:9` 와 같은 방식) |
| 패리티 알고리즘까지 안내 | 범위 밖 (#17·#18). 사실 한 줄만 |
| 힌트를 넣고 싶어짐 | Out of Scope. FR-TR-15 와 충돌한다 |
