# 트레이싱 훈련 - Specification

## 개요

3BLD 학습 앱(cube-study)에 **트레이싱 훈련**을 추가한다. 이슈 #25.

지금 앱은 "케이스 `FU` 가 나왔을 때 뭘 치는가" 는 알려주지만 **"스크램블을 보고 `FU` 라는 걸 알아내는 것"** 은 다루지 않는다. 실전 메모의 대부분이 이 작업이다.

```
스크램블  D R2 F2 L2 U2 B2 U2 F2 D' L2 U F2 R2 F' R' D' B2 D L' B' U R2
   ↓  트레이싱 — 버퍼부터 조각을 따라간다. 이것을 훈련한다
타깃 열   K F B Q C S G J
   ↓  각 쌍이 케이스. 이미 앱이 다룬다 (조회·퀴즈)
실행
```

사용자는 3D 큐브를 손으로 돌려가며 트레이싱하고, 타깃 열을 입력해 채점받는다. **실물 큐브 없이 훈련하는 것이 목적이다.**

**목표 버전**: 0.5.0

---

## 기능 요구사항 (FR)

### 스크램블 생성

- [ ] **FR-TR-1**: 랜덤 스테이트 스크램블을 생성한다. `cubejs` 의 `Cube.random()` → `.solve()` → 뒤집기. TNoodle 과 생성 원리·확률 분포가 같다.
  - `cubejs` 는 이미 `dependencies` 에 있다 (`package.json`). 추가 의존성 없다.
  - 자체 Kociemba 구현이나 TNoodle 포팅은 하지 않는다. 근거는 #22 — pruning table 규모, GPLv3, 무엇보다 자체 구현체를 또 검증해야 한다. 스크램블 분포 편향은 큐브를 돌려봐도 안 보이고 수천 개 통계를 내야 보인다.

- [ ] **FR-TR-2**: 스크램블 생성은 **Web Worker** 에서 한다. 앱 진입 시 `Cube.initSolver()` 를 백그라운드로 돌리고, 완료 후 스크램블 5~10개를 미리 만들어 큐에 적재한다. 소비될 때마다 보충한다.
  - 실측(Node 24.15): `initSolver()` ~1.0초, 생성 27ms. 메인 스레드에서 하면 첫 진입이 멈춘다.
  - 초기화 완료 전에 요청이 오면 "준비 중" 을 표시한다.

- [ ] **FR-TR-3**: 생성 결과는 `{ scramble, core }` 를 함께 낸다. `scramble` 은 표시용, `core` 는 상태 계산용(방향 회전 제외)이다.
  - 방향 회전은 `isSolved()` 를 유지하면서 `asString()` 의 facelet 배치는 바꾼다. 회전이 섞인 문자열로 타깃을 계산하면 문자가 통째로 틀어진다.
  - 이번 범위에서는 방향 무작위화(wide) 를 스크램블 문자열에 붙이지 않는다. FR-TR-12 로 대체한다. 그래도 `core` 분리 규약은 지금 지켜서 나중에 붙일 때 안 깨지게 한다.

### 트레이싱 엔진

- [ ] **FR-TR-4**: 스크램블에서 정답 타깃 열을 계산하는 순수 함수를 만든다. `src/lib/cube/trace.ts` 신설.
  - 입력은 `sim.ts` 의 `CubeState`(`Record<Sticker, Sticker>` — 위치 → 그 자리에 온 스티커의 원래 자리)와 버퍼 정보다. 새 상태 표현을 만들지 않는다.
  - 버퍼에서 시작해 조각을 따라가고, 사이클이 닫히면 남은 미해결 조각으로 끊어 들어간다.

- [ ] **FR-TR-5**: **끊어 들어간 사이클은 닫힐 때 타깃을 하나 더 친다** (버퍼에 파킹해둔 조각 회수). 이것을 빠뜨리면 메모를 실행해도 큐브가 안 풀린다.
  - 근거: 프로토타입에서 이 처리 없이 라운드트립 실패 168건 관측. 넣으니 0건.

- [ ] **FR-TR-6**: 제자리에서 비틀린 코너·뒤집힌 엣지를 **끊기 후보에 그대로 포함시킨다.** 일반 로직이 처리한다(타깃 2개를 먹는 실전 동작까지 재현된다). 엔진 내부에 비틀림 전용 분기를 두지 않는다.
  - 근거: 특례가 있을 때 홀수 타깃 비율이 44.4% 로 이론값에서 벗어났고, 없애니 50.6% 가 됐다. 라운드트립도 285/285(비틀림 제외) → 500/500(전부) 이 됐다.
  - **이것은 관례 A(FR-TR-24)의 정답을 뽑는 경로다.** 관례 B 는 같은 엔진에 "비틀림을 끊기 후보에서 제외" 옵션을 주어 얻는다. 분기는 엔진 바깥의 옵션이지 비틀림 특례가 아니다.

- [ ] **FR-TR-7**: 엔진은 **버퍼를 매개변수로 받는다.** 시그니처는 `trace(state, { pieceKind, bufferStickers, primarySticker })` 꼴이다.
  - 트레이싱 코드에 `'A'` 나 `'UBL'` 같은 상수가 등장하면 안 된다.
  - 버퍼 정보의 출처는 데이터셋 `meta` 하나다 — `meta.buffer` / `bufferStickers` / `primarySticker`.
  - 근거: 프로토타입이 코드 수정 없이 데이터 교체만으로 코너 UBL / 코너 UFR 양쪽에서 378/378 을 냈다. UFR 판(#24)도 동일 스키마 v9 다.

- [ ] **FR-TR-8**: 코너와 엣지를 모두 지원한다. `pieceKind` 만 바뀌고 로직은 같다.
  - 검증됨: 코너 UBL 8.13 / 코너 UFR 8.16 / 엣지 UF 12.23 / 엣지 DF 11.99 (평균 타깃 수), 네 조합 모두 라운드트립·끊기 무작위 통과.
  - 엣지 트레이싱은 **엣지 3-style 데이터(#16) 없이 가능하다.** 트레이싱은 메서드를 모른다.

- [ ] **FR-TR-9**: 코너 스티커의 **회전 방향 순서**를 별도 상수로 둔다. `speffz.ts` 의 `CORNER_FACELETS` 는 `UFL`(U,L,F)과 `DBL`(D,L,B)이 나머지 6개와 반대 방향이다.
  - 지금 코드는 `colorKey` 가 정렬해버려 무해하지만, 방향을 따지는 트레이싱 채점은 여기서 깨진다. 프로토타입 초기 라운드트립 0/260 의 원인이다.
  - 엣지는 스티커가 2개라 방향 문제가 없다.

### 채점

- [ ] **FR-TR-10**: **정답은 하나가 아니다.** 사용자의 타깃 열을 실행 모델(타깃 하나 = 버퍼 조각과 그 자리의 교환)에 넣어 조각이 전부 풀리면 정답이다. 문자열 비교로 채점하지 않는다.
  - 끊기 지점 선택이 자유라 한 스크램블에 유효한 메모가 **평균 11가지**(최대 21) 나온다.
  - 기존 원칙의 연장이다 — README: "채점은 문자열 비교가 아니라 실제 큐브 효과로 판정한다".

- [ ] **FR-TR-11**: 부분 채점. 타깃을 하나씩 적용하며 **첫 어긋난 지점**을 짚는다.
  - 판정 기준은 "지금 버퍼에 있는 조각이 이 자리에 **방향까지** 맞게 들어가는가" 다. 378 = 42 큐비쌍 × 9 방향이므로 방향을 안 보면 채점이 성립하지 않는다.
  - 끊기 시점에는 "미해결·미방문 조각의 스티커인가" 만 본다. 어느 조각, 어느 스티커든 허용한다.

- [ ] **FR-TR-12**: 타깃 수가 정답보다 많으면 **불필요한 끊기**로 구분해 알린다. 풀리기는 하므로 오답이 아니다.
  - 근거: 끊기 지점을 무작위로 골라도 타깃 수는 불변이다(400/400 확인). 개수는 스크램블이 정한다.

- [ ] **FR-TR-24**: **비틀림 처리 관례를 세션 설정으로 고른다.** 정답 타깃 열이 관례에 따라 다르다.
  - **관례 A (기본)** — 제자리 비틀림도 끊어 들어가 타깃 2개로 처리한다. letter 열에 포함된다. OP/M2 입문의 방식이고 현재 사용자가 쓰는 방식이다.
  - **관례 B** — 비틀림을 letter 열에서 빼고 **비틀림 전용 알고리즘**으로 따로 친다. 3-style 숙련의 방식이다. 타깃 열과 별도로 **비틀림 목록**이 생긴다.
  - 측정된 차이 (무작위 3000상태 중 비틀림 관련):

    | | 해당 상태 | 평균 타깃 A → B |
    |---|---|---|
    | 코너 UBL | 1475 (49%) | 8.79 → 6.37 |
    | 엣지 UF | 1209 (40%) | 12.87 → 10.61 |
    | 엣지 DF | 1134 (38%) | 12.90 → 10.56 |

  - **관례 B 에서는 버퍼 자신이 비틀린 채 남는다 — 코너 80.9%, 엣지 77%.** 방향 합이 보존되므로 다른 비틀림을 남기면 버퍼가 보정을 떠안는다. 비틀림 목록에 버퍼가 포함될 수 있어야 한다.
  - 패리티는 관례와 무관하다. 비틀림 하나가 타깃 2개라 홀짝이 안 바뀐다 (코너·엣지 전 표본 일치). FR-TR-13 은 그대로다.
  - 채점: 실행 후 **전부 풀림**(A) 또는 **사용자가 선언한 비틀림만 남음**(B) 이면 정답이다.
  - 결과 화면에서 두 관례의 타깃 수를 함께 보여준다. 3-style 로 넘어갈 때의 이득이 그대로 보인다.

- [ ] **FR-TR-25**: 비틀림 표기는 **문자 하나**다. 방향 마커(`K'` 등)를 쓰지 않는다.
  - 코너 규칙: **U/D 색 스티커가 지금 앉아 있는 자리의 문자**를 부른다. 코너는 U 또는 D 색 스티커를 정확히 하나 갖고, 제자리 비틀림 상태는 둘뿐이라 그 스티커가 앉는 자리도 정확히 둘이다 — 문자 하나로 방향까지 특정된다.
    - 검증: 제자리 비틀린 코너 2053건 전부 특정 가능, 큐비당 정확히 2가지 자리.
    - 사람이 쓰는 방식과 같다 — "흰 스티커가 F 면에 와 있다" 가 곧 방향이다.
  - 엣지 규칙: 제자리 뒤집힘은 상태가 하나뿐이라 큐비를 지목하는 문자면 된다.
  - 버퍼 비틀림도 같은 규칙으로 적힌다. 버퍼 스티커 문자(UBL 이면 `E`/`R`)는 타깃 열에 나올 수 없으므로 충돌하지 않는다.

- [ ] **FR-TR-13**: 결과 화면에 **패리티 여부**를 표시한다. 코너 타깃이 홀수면 패리티다.
  - 근거: HANDOFF §4.6 — 3-style·M2 둘 다 EVEN 이라 ODD 순열을 못 품고, 마지막 하나를 OP Y-perm 으로 처리해야 한다. 훈련 자체는 실행을 안 하지만 이 정보가 학습에 직결된다.

### 화면

- [ ] **FR-TR-14**: 큐브는 **3D 로 보여준다. 전개도를 쓰지 않는다.**
  - 전개도는 24면을 한 번에 보여주므로 훈련하려는 기술이 사라진다. 실전에서 3면만 보이니까 버퍼부터 따라가는 것이다.
  - 3D 뷰어 구현은 #13 이다. `three` 직접 조립, 면별 임의 색, `OrbitControls` 드래그 회전.

- [ ] **FR-TR-15**: **뒷면이 회전 없이 새어나가면 안 된다.** 힌트 스티커, 반투명, 미니맵, 전개도 보조 표시를 이 화면에 두지 않는다. 실물과 같이 돌려야 보이는 상태를 유지한다.

- [ ] **FR-TR-16**: 3D 뷰어는 버퍼 / 현재 타깃 / 이미 지나간 조각을 **동시에 서로 다른 색**으로 칠할 수 있어야 한다. 지나간 조각은 개수가 계속 늘어난다(코너 평균 8 + 엣지 평균 12).
  - 전 면 회색(FR-TR-22)도 같은 경로로 칠한다. 뷰어는 "무슨 색을 어디에" 만 받는다.
  - 하이라이트를 색으로만 구분하지 않는다(테두리 등 이중 부호화). 색약 고대비 모드는 별도 이슈다.

- [ ] **FR-TR-17**: 스크램블 방향 무작위화를 **초기 카메라 각도 무작위화로 대체한다.** 24방향 중 하나에서 시작한다.
  - 원래 wide move 는 "큐브를 받았을 때 방향을 다시 파악하는 시간" 을 넣으려는 것이다. 3D 는 어차피 사용자가 돌리므로 카메라로 같은 효과가 난다.

- [ ] **FR-TR-18**: 타깃 열 입력은 **온스크린 24글자 패드**로 한다. 하드웨어 키보드 입력도 함께 받는다.
  - 0.1.0 SPEC 이 미뤄둔 항목이 여기서 돌아온다 — `SPEC.md:242` "온스크린 스티커 입력 패드 | 0.2.0 이후 재검토".
  - 코너는 대문자, 엣지는 소문자로 구분한다 (`speffz.ts` 의 `CORNER_INDEX` / `EDGE_INDEX` 표기를 따른다).
  - 입력 중 삭제·전체 지우기가 가능하다.
  - **입력 구획을 둘로 나눈다** — "타깃 열" 과 "비틀림". 실전이 letter 열과 twist 를 따로 담는 것과 같다. 비틀림 칸은 **순서를 채점하지 않는다**(집합으로 본다). 관례 A(FR-TR-24)를 고르면 비틀림 칸은 비활성되고 전부 타깃 열에 들어간다.

- [ ] **FR-TR-19**: 세션 시작 시 **훈련 대상**을 고른다 — 코너만 / 엣지만 / 코너 → 엣지 이어서.
  - 실전은 이어서 하고, 그때 코너 파지가 가장 어려운 지점이 된다.

- [ ] **FR-TR-20**: 채점 후 정답 타깃 열 하나를 예시로 보여준다. 정답이 여럿임을 함께 알린다(FR-TR-10).

- [ ] **FR-TR-21**: 훈련 모드가 둘이다. 세션 시작 시 고른다.
  - **보고 따라가기** — 큐브를 보면서 타깃을 하나씩 입력한다. 입력 중에도 큐브가 계속 보인다. 트레이싱 규칙 자체를 익히는 단계다.
  - **외운 다음 입력하기** — 큐브를 보며 트레이싱해 머릿속에 담고, "다 외웠다" 를 누르면 **큐브가 사라진 뒤** 입력한다. 실전과 같은 순서다.
  - 두 모드는 같은 엔진·같은 채점을 쓴다. 다른 것은 입력 시점에 큐브를 보여주는지 여부뿐이다.

- [ ] **FR-TR-22**: 시작 전 큐브는 **전 면이 회색**이다. 시작 버튼을 누르면 스크램블 상태의 색이 입혀지고 그 순간부터 시간이 흐른다.
  - 준비 상태와 시작 시점이 눈으로 구분된다. 스크램블을 미리 훔쳐보고 시작하는 것도 막는다.
  - 회색 상태에서도 큐브를 돌려볼 수 있다 — 카메라 각도를 미리 잡아두기 위해서다.

- [ ] **FR-TR-23**: 트레이싱에 걸린 시간을 잰다.
  - 측정은 `performance.now()` 로 한다. `Date.now()` 는 시스템 시계 조정에 영향받는다.
  - 시작은 FR-TR-22 의 색이 입혀지는 순간, 종료는 **모드에 따라 다르다** — "보고 따라가기" 는 마지막 타깃 입력, "외운 다음 입력하기" 는 **"다 외웠다" 를 누른 시점**(입력 시간은 트레이싱 시간이 아니다).
  - 결과 화면에 이번 시간과 직전 기록들을 함께 보여준다.

## 비기능 요구사항 (NFR)

- [ ] **NFR-TR-1**: Kociemba 풀이기는 **Web Worker 안에서만 초기화하고, 트레이싱 화면을 벗어날 때 `terminate()` 로 반납한다.**
  - **이유는 번들 크기가 아니다.** 실측: `solve.js` 는 raw 28.8KB / **gzip 7.1KB** 다 (`cube.js` 는 22.4KB / gzip 4.6KB). 7KB 를 피하려고 설계를 비틀 이유는 없다.
  - 비용은 런타임이다. `Cube.initSolver()` 실측 **1695ms, heap +37MB, RSS +102MB**. pruning table 을 메모리에 올리는 값이다. 메인 스레드에 있으면 1.7초 멈추고 100MB 를 계속 붙들며, 조회·퀴즈만 쓰는 사용자도 그 메모리를 떠안는다. Worker 면 통째로 반납된다.
  - 구현은 Vite 표준 패턴이면 된다 — `new Worker(new URL('./scramble.worker.ts', import.meta.url), { type: 'module' })`. 설정 트릭 없이 별도 청크로 갈라진다. `cubejs` 자체 async API(`lib/async.js`)는 `window.Worker` 와 워커 URI 를 전제하므로 쓰지 않고 워커를 직접 짠다.
  - **`solve.js` 코드가 메인 청크에 섞이는 것 자체는 허용한다** (gzip 7KB). 금지 대상은 메인 스레드에서의 `initSolver()` 호출이다.
  - 검증: 빌드 산출물에서 Worker 청크 분리 확인 + 트레이싱 화면 진입 전 메인 스레드 메모리가 튀지 않는지 확인.

- [ ] **NFR-TR-2**: `three`(gzip ~85KB)는 **지연 로드**한다. 트레이싱·3D 화면에 들어갈 때만 받는다. alternatives 데이터와 같은 방식이다.

- [ ] **NFR-TR-3**: PWA 오프라인 동작을 깨지 않는다. 런타임 네트워크 요청을 추가하지 않는다.

- [ ] **NFR-TR-4**: 트레이싱 엔진은 **화면 없이 단위 테스트로 전부 검증된다.** 순수 함수로 만들고 렌더링·입력에 의존하지 않는다.

- [ ] **NFR-TR-5**: dry 한 정보 앱 톤을 유지한다(기존 NFR-9). 연속 정답 배지, 축하 연출, 점수 랭킹을 넣지 않는다.

- [ ] **NFR-TR-6**: 상태 갱신은 Svelte `$state` 반응성으로 한다. 수동 DOM 조작을 쓰지 않는다. 3D 캔버스는 예외 — `three` 가 자체 렌더 루프를 돈다.

## 제약

- **기록은 소요 시간만 남긴다.** 솔브 레코드·케이스별 약점 통계·추이 그래프는 이번 범위 밖이다(#23).
  - 저장 필드는 `{ at, ms, pieceKind, buffer, mode, twistConvention, targetCount, correct }` 로 최소화한다.
  - **`twistConvention`(A/B)을 포함한다.** 관례가 타깃 수를 평균 2.4개 바꾸므로(FR-TR-24), 이 값이 없으면 기록끼리 비교가 성립하지 않는다. `buffer` 를 넣는 것과 같은 논리다.
  - **`buffer` 를 반드시 포함한다.** 같은 스크램블도 버퍼가 다르면 정답이 다르다 — UBL `K F B Q C S G J` vs UFR `S G A K F A B Q`. 나중에 갈라면 마이그레이션이 된다(#20 항목 2).
  - **저장 키와 스키마 버전을 암기 체크와 분리한다.** `src/lib/domain/memorize.ts:51` 의 `parseStored` 는 `schemaVersion` 불일치 시 저장물을 전부 버린다. 같은 키에 얹으면 암기 진도가 날아간다.
  - 보관 개수 상한을 둔다(최근 N건). 무한히 쌓이지 않게 한다.

- **버퍼 하드코딩 금지.** FR-TR-7. 기본은 UBL(코너)·UF(엣지)지만 코드가 그것을 알면 안 된다.

- **케이스 데이터에 의존하지 않는다.** 트레이싱은 알고리즘을 모른다. `corner-UBL.json` 은 검증(378 케이스 왕복 테스트)에만 쓰고 런타임 경로에서는 읽지 않는다.

- **자체 큐브 물리 금지.** 무브의 효과는 전부 `cubejs` 가 안다. 0.3.0 까지 `L` 이 뒤집힌 채 나갔던 전례가 있다 (`speffz.ts` 주석).

- **기술 스택 고정**: SvelteKit 2 + TypeScript + `adapter-static` + `@vite-pwa/sveltekit`. 정적 빌드.
