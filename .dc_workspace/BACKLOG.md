## 다국어 (i18n) — 0.2.0 후보

### 요구사항

- **지원 언어: en, ko 두 개만.** 그 이상 늘리지 않는다.
- **기본 언어는 시스템/브라우저 언어에서 가져온다** (`navigator.language`).
- 사용자가 선택하면 **localStorage 에 저장**하고 그 선택이 시스템 설정을 이긴다.
  (테마와 동일한 3단 구조: `system` / `en` / `ko` — `ui.theme` 와 같은 패턴)
- 전환 UI 는 **국기 아이콘** 등으로. 상단 바를 새로 만들거나 기존 하단 네비게이션에 얹는다.
  현재 상단 바에는 테마 토글만 있으므로 그 옆이 자연스럽다.

### 확정된 번역

토글 라벨은 영문을 유지할지 번역할지 결정이 필요하다. 사용자가 준 대응은 아래와 같다.

| 영문 | 한국어 |
|---|---|
| setup | 셋업 |
| optimized | 최적 |
| structural | 구조화 |
| compact | 간략화 |

### 번역 대상 정리

| 영역 | 번역 | 비고 |
|---|---|---|
| 네비게이션 (조회/기준공식/퀴즈) | O | |
| 토글 라벨 | 위 표 | |
| 토글 설명 줄 (`기준공식 + 셋업` 등) | O | |
| 무효 입력 사유 | O | **조사 처리 주의** — `josa()` 는 한국어 전용이다 |
| 퀴즈 판정 문구 | O | |
| 타깃 위치 표기 (`L = DFL의 F면`) | O | 영문은 `L = F face of DFL` 형태 |
| 큐브 표기 (`R U R' U'`) | **X** | 만국 공통 |
| 케이스 코드 · 기준공식 이름 (`LB`, `SC`) | **X** | Speffz 는 영문 고정 |
| 큐비 이름 (`UBL`, `DFR`) | **X** | 만국 공통 |

### 구현 시 주의

- `validate.ts` 의 `josa()` 는 한국어 조사(은/는, 와/과) 처리다. 영어에는 없는 개념이므로
  문구 조립을 언어별 함수로 분리해야 한다. 현재 `reasonText()` 가 문자열을 만드는 구조라
  이 지점을 언어 레이어로 빼는 것이 첫 작업이 된다.
- `verdictText()` 도 같은 성격이다.
- `<html lang>` 을 선택 언어에 맞게 갱신해야 한다. 현재 `ko` 하드코딩.
- PWA manifest 의 `lang` / `name` / `description` 도 언어별 처리를 검토한다.
  (manifest 는 빌드 타임 고정이라 한쪽만 택하거나 `lang` 을 중립으로 두는 선택이 필요)
- 라이브러리 도입 여부: 문구 수가 30개 안팎이라 `paraglide` 같은 도구 없이
  단순 사전 객체 + `$derived` 로 충분할 가능성이 높다. 번들 최소 원칙(GLOBAL 1절)과도 맞는다.
- E2E 는 현재 한국어 문구를 직접 검증하는 곳이 있다(`3-cycle이 아닙니다` 등).
  언어 전환 후에도 통과하도록 테스트를 언어 중립 셀렉터(`data-verdict` 등)로 옮기거나
  언어를 고정하고 돌려야 한다.

### 우리가 만들 때 쓸 규약

`BoxGeometry` 는 **면마다 material 인덱스가 따로**다. Mesh 에 배열을 넘기면 면별로 다른
색이 된다. 인덱스 순서는 three.js 규약이고 위 참고 구현도 같은 순서를 쓴다.

```
0: +X   1: -X   2: +Y   3: -Y   4: +Z   5: -Z
```

```js
const mesh = new THREE.Mesh(boxGeom, [m0, m1, m2, m3, m4, m5]);
```

참고 구현은 mask 로 "겉면인가" 만 판정해 표준 6색을 넣고 `materialArrayCache` 로 mask 별
캐시를 둔다. **우리는 그 캐시를 걷어내야 한다** — 같은 mask 라도 큐비마다 색이 달라진다.

우리 쪽 입력은 이미 있다.

- `src/lib/cube/speffz.ts` 의 `CORNER_FACELETS` / `EDGE_FACELETS` 가 큐비 → facelet 인덱스를
  들고 있다 (예: `UBL: [0, 36, 47]`). 이것과 (큐비, ±축) 을 맞물리면 어느 면에 어느 스티커
  문자가 오는지 나온다
- `sim.ts` 가 `{ 위치: 원래_스티커 }` 상태를 낸다

즉 렌더러는 무브를 모르고 상태만 그리면 된다. 0.3.1 에서 정한 "무브의 물리는 저장소에
두지 않는다" 와 충돌하지 않는다.

3-style 학습 용도로는 버퍼(UBL)와 타깃 2개를 서로 다른 색으로 칠하는 것이 목적이므로,
material 3개를 갈아끼우는 수준이면 된다.

### 탈락: `cubing` (cubing.js)

큐브 전용이고 `<twisty-player>` 웹 컴포넌트에 드래그 회전이 이미 들어 있어서 가장
유력해 보였지만, **면에 임의 색을 못 넣는다.**

type StickeringMask      = { orbits: Record<string, OrbitStickeringMask> }
type OrbitStickeringMask = { pieces: (PieceStickeringMask | null)[] }
type PieceStickeringMask = { facelets: (FaceletMeshStickeringMask | ... | null)[] }

## 기기 간 학습 진도 동기화 — QR 전송 (0.5.0 후보)

폰과 탭을 오가며 암기하는데 진도가 안 맞는다. 2026-08-18 에 방식을 검토했다.

### 결론: QR 코드로 기기 간 직접 전송. 서버도 로그인도 없다.

학습 상태는 결국 **케이스당 2비트**다 (setup 체크, direct 체크). 378 × 2 = 756비트
= **95 bytes**. 헤더까지 99 bytes 면 QR 버전 10 / 오류정정 H 로 들어간다 (57×57 모듈).
H 는 30% 손상돼도 복원되므로 화면을 사진 찍는 정도의 반사·기울기는 문제가 안 된다.

지금 저장 형식(`{setup: string[], direct: string[]}`)을 그대로 넣으면 최대 3,832 bytes
라 QR 최대 용량(2,953 bytes)을 넘겨 **안 들어간다.** 비트셋으로 접는 것이 필수다.

얻는 것:

- 우리 서버가 안 생긴다. `adapter-static` 그대로
- 계정·OAuth·구글 클라우드 프로젝트 설정이 없다
- 남의 학습 기록을 우리가 보관하지 않는다
- 인터넷 자체가 필요 없다. 화면 대 카메라라 비행기 모드에서도 된다
- **저장 스키마를 안 건드려도 된다** — 비트셋은 전송 형식일 뿐이다. `memorize.ts` 의
  `SCHEMA_VERSION` 을 올리지 않으므로 기존 진도가 날아갈 위험 구간이 통째로 없다

감수하는 것:

- 자동이 아니다. 기기를 바꿀 때 사람이 한 번 찍는다 ("오가면서 자동" 이 아니라 "옮길 때 5초")
- 병합이 제한적이다. 비트셋 OR 로 합치면 진도 유실은 없지만 **체크 해제는 안 옮겨진다.**
  암기 진도는 대체로 늘기만 하므로 OR 이 실용적이다. 다만 화면에 명시해야 한다

### 전송 페이로드에 무엇을 넣을 것인가

**`meta.schemaVersion` 으로 거르면 안 된다.** 비트 위치가 의존하는 것은 스키마 버전이
아니라 **케이스 코드 집합과 그 정렬 순서**다. 0.3.1 이 정확히 그 반례다 — schemaVersion 은
8 → 9 로 올랐지만 (알고리즘의 `L`↔`L'` 표기 수정) 케이스 코드 집합과 배정은 하나도 안
바뀌었다. schemaVersion 으로 걸렀다면 멀쩡한 전송을 거부했을 것이다.

반대 방향의 사고도 가능하다. schemaVersion 이 그대로인 채 케이스가 추가되면 같은 비트가
다른 케이스를 가리키는데 검사를 통과한다.

그래서 헤더에는 **정렬한 케이스 코드 목록의 해시**를 넣는다. 그것이 비트 위치가 실제로
기대는 유일한 값이다.

| 필드 | 크기 | 용도 |
|---|---|---|
| 페이로드 형식 버전 | 1 byte | 인코딩 자체가 바뀔 때 |
| 케이스 코드 집합 해시 | 2 bytes | 비트 위치의 정합성. 현재 값 `d24c` (sha256 앞 2바이트) |
| 체크섬 | 1 byte | QR 오류정정을 통과한 뒤의 최종 확인 |
| 비트셋 | 95 bytes | 케이스당 2비트, 코드 정렬 순 |

해시가 다르면 거부하고 "데이터 버전이 다릅니다" 를 띄운다. 조용히 잘못 적용하는 것보다 낫다.

| OR 병합 + 해시 불일치 거부 | ~60줄 + 테스트 |
| QR 생성 | ~50줄 |
| 스캔 화면 (카메라 + 붙여넣기 폴백) | ~200줄 |
| UI (내보내기/가져오기 진입점, 확인 절차) | ~100줄 |

0.5.0 하나로 충분하다. E2E 는 카메라 모킹이 필요하지만 외부 인증이 없어 훨씬 쉽다.

### 검토했다가 접은 것: 구글 로그인 + 서버 동기화

원래 요구는 "구글 로그인으로 자동 싱크" 였다. 접은 이유는 돈이 아니다 — Google Identity
Services 와 OAuth 2.0 은 과금이 없다. **복잡도가 비용이다.**

- 홈서버에 백엔드를 얹으면 "정적 파일뿐이라 서버 런타임은 없다" 는 불변식이 깨진다
  (`deploy/README.md`). systemd 서비스, 백업, 시크릿 관리, 배포 대상 둘
- 관리형 백엔드(Cloudflare Workers / Supabase)는 무료 티어 안이지만 외부 의존이 늘고
  배포 대상이 둘이 된다
- 사용자 Drive 의 `drive.appdata` 에 쓰면 서버는 없지만 토큰 갱신과 구글 의존이 남는다
- 어느 쪽이든 **오프라인 양쪽 편집의 병합**이 진짜 난제다. 지금 저장 형식은 집합이라
  시각 정보가 없어서, 항목별 타임스탬프(LWW)를 넣으려면 저장 스키마를 v2 로 올리고
  마이그레이션을 짜야 한다. `parseStored` 가 `schemaVersion` 불일치 시 전부 버리므로
  (`src/lib/domain/memorize.ts`) 마이그레이션을 틀리면 진도가 날아간다

자동 싱크가 정말 필요해지면 그때 다시 꺼낸다. QR 로 충분한지 먼저 써보고 판단한다.

## 상단 바 햄버거 메뉴 — 착수 문턱

2026-08-18 에 "슬슬 햄버거로 통합할 때인가" 를 검토했고 **아직 아니다** 로 결론냈다.
나중에 같은 질문을 다시 처음부터 논의하지 않도록 문턱만 적어둔다.

### 지금 상태

`+layout.svelte` 의 상단 바에 버튼이 4개 있지만, **설치 버튼은 조건부다** —
`beforeinstallprompt` 가 떠야 나오고 `appinstalled` 에서 사라진다. 이미 설치해서
쓰는 기기에는 영원히 안 뜬다. 실제로 보이는 것은 **화면 켜기 / 테마 / 정보 3개**다.

폭도 남는다. 실측:

| 뷰포트 | 버튼+간격 | 여유 |
|---|---|---|
| 320px | 125px | 195px |
| 360px | 216px | 144px |
| 412px | 216px | 196px |

320px 에서는 라벨이 접혀 아이콘만 남고(37px씩) 그래도 195px 이 남는다. 지금 크기의
버튼을 4개 더 넣어도 안 넘친다. **폭은 제약이 아니다.**

### 지금 접으면 손해다

- 모든 항목이 탭 한 번씩 멀어진다
- **화면 켜기의 상태가 안 보이게 된다.** 켜짐을 색으로 드러내는 것이 이 버튼의 요점이다 —
  큐브를 돌리는 중에 화면이 꺼질지를 눈으로 알아야 한다. 메뉴 안에 들어가면 열어봐야 안다
- 테마도 같은 이유로 현재 상태를 아이콘이 표시하고 있다

### 문턱

- **상태를 표시하는 버튼은 끝까지 밖에 둔다** (화면 켜기, 테마). 숨기면 기능이 죽는다
- **동작만 하는 항목이 3개를 넘으면** 그것들만 햄버거로 접는다

지금 동작 항목은 "정보" 하나다. 상단 바로 올 후보가 백로그에 줄줄이 있다.

| 후보 | 출처 |
|---|---|
| 언어 전환 (국기 아이콘) | i18n 절이 "상단 바 테마 토글 옆" 으로 지목 |
| 진도 내보내기/가져오기 | QR 전송 절 |
| 3D 뷰어 진입점 | 3D 큐브 뷰어 절 |

셋 중 둘이 들어오면 동작 항목 3개, 그 다음 하나가 붙는 순간이 착수 시점이다.

## 디자인 시스템 — 아직 아님, 착수 신호만 정해둠

Claude Design (`design` 스킬 / `DesignSync`)으로 디자인 시스템을 세울 수 있는지
검토했다. **된다. 다만 지금은 하지 않는다.**

### 왜 지금이 아닌가

**디자인 시스템은 발명이 아니라 추출이다.** 지금 UI 컴포넌트가 11개인데
(`SegToggle` `StickerPad` `MoveKeypad` `AnchorPad` `CaseInput` `CaseView` `Alg`
`Cube3D` `Records` `Toast` `UpLink`), 두 화면 이상에서 실제로 재사용되는 것은
`SegToggle` · `Alg` · `UpLink` 정도다. 나머지는 아직 한 화면짜리다. 지금 규격으로
뽑으면 **우연히 그렇게 생긴 것**을 굳힌다.

**중요한 절반은 이미 있다.** `src/lib/styles/app.css` 의 토큰이 사실상 색 레이어다
— `--bg` `--surface` `--fg` `--muted` `--border` `--insert` `--interchange` `--ok`
`--danger` `--accent` 에 라이트/다크/시스템 3단. 0.4.1 에서 OKLCh 로 명도까지 맞췄고
(#26 이 그 측정값을 출발점으로 삼는다고 적혀 있다). 남은 것은 시각적 카탈로그인데
그것은 **사람이 여럿일 때** 값이 나온다. 지금은 만드는 사람과 쓰는 사람이 같다.

**정본이 둘이 된다.** 화면 규약을 `.dc_workspace/CONVENTIONS.md` 하나로 모으기로
한 것(`2026_08_24-navigation/SPEC.md` FR-NAV-15)과 같은 문제다. 디자인 시스템
프로젝트를 지금 세우면 그 둘이 갈라지고, 관리 비용이 얻는 것보다 크다.

### 착수 신호 (#14 의 문턱과 같은 방식)

| 신호 | 왜 그때인가 |
|---|---|
| **#26 색각 고대비 모드** | 팔레트가 **두 벌**이 되는 순간. 토큰 세트가 복수가 되면 손으로 관리하는 지점을 넘는다. 가장 강한 신호다 |
| **#19·#21·#23 중 둘** | 훈련 화면이 3~4개가 되면 `SegToggle`·판정 줄·진행 버튼이 6~7개 화면에서 반복된다. 재사용이 그때 진짜가 된다 |
| **#15 i18n** | 라벨 길이가 변수가 된다. 컴포넌트가 길이에 견디는지를 카탈로그로 보는 값이 생긴다 |

셋 중 **둘**이 들어오면 그때다. 그 전에는 `CONVENTIONS.md` 가 디자인 시스템의
글자 절반을 대신한다.

### 목업도 이 앱에서는 값이 낮다

일회용 목업(예: 진행 버튼 자리 ⓐ/ⓑ/ⓒ 비교)조차 권하지 않는다. 지금 풀고 있는
문제가 통째로 **세로 예산**이고, 그것은 실제 폰의 폰트·주소 표시줄·터치 타깃이
있어야 정확하다. HTML 아트보드는 그것을 재현하지 못한다. `deploy/deploy.sh` 가
20초면 끝나므로 **두 안을 실제로 만들어 배포하고 폰에서 눌러보는 편이 더 빠르고
정확하다.**

두 도구의 차이도 적어둔다 — `design` 스킬은 아트보드 캔버스(목업)를 만들고,
`DesignSync` 는 claude.ai 의 디자인 시스템 프로젝트와 **로컬 컴포넌트 라이브러리**를
컴포넌트 단위로 동기화한다. 위 신호가 왔을 때 필요한 것은 후자다.
