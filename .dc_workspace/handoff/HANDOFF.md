# HANDOFF — 3-Style Corner Trainer 프로젝트 배경

이 문서는 `INSTRUCTIONS.md`(무엇을 만들지)와 짝을 이루는 **왜 이렇게 만드는지**에 대한 맥락 문서입니다.
Claude Code가 구현 중 판단이 필요할 때 이 문서를 근거로 삼으세요.

---

## 1. 사용자 프로필

- 한국 거주 개발자. 웹/백엔드(FastAPI, PostgreSQL, WordPress) 및 서버 운영 경험 있음
- 집에 Ubuntu 서버 운영 중 (nginx, DuckDNS, acme.sh 인증서). **배포 인프라 이미 보유**
- 개발 환경: Ubuntu, zsh, JetBrains 계열 IDE
- **학습 스타일이 중요**: 규칙 암기보다 구조·원리 이해를 선호. "왜 이렇게 되는가"를
  공간적/수학적으로 설명하면 훨씬 잘 받아들임. 이 성향이 앱 설계에 직접 반영되어야 함
  (→ 단순 알고리즘 나열이 아니라 A/B 파트 분해, 입구 자리, 구조 표시를 중시하는 이유)
- 정확성에 민감. 근거 없는 단정을 싫어하고, 틀린 내용은 직접 지적함

### 큐빙 현황 (2026년 8월 기준)

| 항목 | 현재 상태 |
|---|---|
| 메서드 | 코너 OP(Old Pochmann) + 엣지 M2, 버퍼 UBL |
| 3BLD 평균 | 약 6분 (메모 3~4분 + 실행 2~3분) |
| 성공률 | 약 50% |
| 주요 실패 원인 | 메모 실수 (letter pair 단어화가 즉석에서 안 되는 조합) |
| 장기 목표 | MBLD (멀티 블라인드) |
| 3-style 진행도 | **아직 학습 시작 전.** 개념 이해 단계 |

**중요**: 사용자는 3-style을 아직 안 배웠습니다. 이 앱은 **학습 시작을 돕는 도구**이지
숙련자용 레퍼런스가 아닙니다. UI가 입문자에게 친절해야 합니다.

## 2. 이 앱이 나온 경위

대화 흐름 요약:

1. BLD 타이머 앱 비교 (csTimer / Flowtimer) → csTimer만 멀티페이즈 지원 확인
2. 3BLD 정체 원인 분석 → 메모가 병목, letter pair 시스템 필요
3. OP 코너의 break-in 추적이 어렵다는 호소 → 3-style이 대안으로 등장
4. commutator 원리 학습 (ABA'B' 구조, 왜 비대칭인지, 왜 4-style은 불가능한지)
5. PDF 자료 제작 → 개념편, 전용 완전판(UBL/UFR), 셋업 방식 완전판, 입구 요약
6. **"PDF를 폰에서 빠르게 찾아보고 싶다"** → 이 앱

즉 **PDF의 조회 불편함을 해결하는 것**이 1차 목적입니다. 378개 표를 PDF에서 스크롤로
찾는 건 연습 중에 불가능하니까요.

## 3. 핵심 설계 결정과 그 이유

### 3.1 왜 direct / setup 두 가지 알고리즘을 다 넣는가

학습 경로가 두 단계이기 때문입니다:

- **초기**: 기준공식 10개만 외우고 셋업으로 378개를 다 처리 (setup 모드)
- **숙련**: 자주 나오는 케이스부터 전용 최적 알고리즘으로 교체 (direct 모드)

사용자는 **초기에 setup 모드를 주로 쓰다가 점차 direct로 이동**할 것입니다.
따라서 두 모드 전환이 매끄러워야 하고, 케이스별로 "나는 이걸 direct로 익혔다"를
표시할 수 있으면 이상적입니다.

이 두 방식은 트레이드오프 관계입니다:

| | 외울 양 | 평균 길이 |
|---|---|---|
| setup | 기준 10개 | 11.2수 |
| direct | 378개 | 8.9수 |

### 3.2 왜 A/B 파트를 따로 표시하는가

사용자는 M2 메서드를 배울 때 **"셋업 무브를 외우지 말고 어디로 옮기는지 생각하라"**는
설명 방식으로 성공한 경험이 있습니다. 알고리즘을 통짜로 외우는 대신 구조로 이해하는 방식입니다.

3-style도 같은 접근이 가능합니다:
- **A (인서트)**: 평면 밖 조각을 빈자리로 데려왔다 돌려보내는 3수 덩어리
- **B (교환)**: 한 무브로 두 조각을 맞바꿈

`A B A' B'` 4토막을 시각적으로 구분해서 보여주면 통암기 부담이 크게 줄어듭니다.
**이건 부가 기능이 아니라 이 앱의 핵심 가치입니다.**

### 3.3 왜 기준공식의 "입구 자리"를 표시하는가

setup 모드에서 셋업 무브를 즉석에서 만들려면 **"어디로 옮겨야 하는지"**를 알아야 합니다.
그게 입구 자리입니다. 예: 기준 LB의 입구는 `L = DFL의 F면`, `B = UBR의 U면`.

셋업 = "내 케이스의 두 타깃 조각을 이 두 입구로 옮기는 무브".

M2와 다른 점: M2는 타깃 **하나**만 옮겼지만, 3-style은 **둘**을 동시에 맞춰야 합니다.
이게 셋업을 어렵게 만드는 지점이고, 그래서 입구 표시가 중요합니다.

### 3.4 왜 버퍼가 UBL인가

사용자의 현재 OP 메서드가 UBL 버퍼입니다. **letter scheme을 그대로 재사용**할 수 있어
학습 진입 비용이 최소입니다.

UFR 버퍼가 3-style 커뮤니티 표준이고 알고리즘 효율도 약간 낫지만:
- letter scheme 재학습 필요
- **OP fallback이 불가능해짐** (OP는 UBL이라 메모가 호환 안 됨)
- 전환기에 3BLD 기록이 크게 나빠짐

그래서 **UBL로 시작 → 나중에 엣지 3-style로 갈 때 UFR 재검토**로 결정했습니다.
UFR 데이터도 이미 만들어둔 상태이므로(378케이스), 나중에 같은 스키마로 추가 가능합니다.

### 3.5 왜 "엣지 무영향"이 중요한가

BLD 표준 순서는 **엣지 먼저 → 코너 나중**입니다. 코너 알고리즘이 엣지를 건드리면
이미 푼 엣지가 깨집니다.

이 프로젝트 초기에 실제로 이 버그가 있었습니다 — 첫 PDF의 pure 커뮤테이터 198개 중
**80개가 엣지를 오염**시켰습니다. 엣지 무영향 조건을 넣고 재탐색해서 수정했습니다.

**따라서 데이터의 알고리즘을 임의로 바꾸거나 "더 짧은 걸 찾아" 교체하지 마세요.**
길이만 보고 최적화하면 이 조건이 깨집니다.

### 3.6 왜 PWA인가

- 필요 기능(조회, 검색, 로컬 저장, 오프라인, 나중에 타이머·퀴즈·3D)이 전부 웹 범위 안
- 사용자가 웹 개발자이고 서버 인프라를 이미 보유
- 데스크탑에서도 같은 앱 사용 가능
- 안드로이드 스튜디오·APK·스토어 불필요

**오프라인 요구가 강합니다.** 설치 후에는 네트워크 없이 완전히 동작해야 합니다.
데이터가 176KB뿐이라 전부 번들에 넣으면 됩니다.

PWA로 안 되는 것은 두 가지뿐이고, 둘 다 현재 계획에 없습니다:
- 홈 화면 위젯 (네이티브 필요)
- 블루투스 스마트큐브 연동 (iOS 미지원, 계획 없음)

## 4. 도메인 지식 — 틀리기 쉬운 부분

구현 중 헷갈릴 수 있는 것들입니다. **여기 적힌 내용은 큐브 시뮬레이터로 검증된 사실입니다.**

### 4.1 버퍼 스티커는 케이스에 안 나온다

버퍼(UBL)의 스티커 `A`, `E`, `R`은 **읽는 위치**이지 타깃이 아닙니다.
케이스 코드에 절대 등장하지 않습니다. 입력 검증에서 거부해야 합니다.

### 4.2 같은 큐비의 두 스티커는 케이스가 아니다

`B`와 `N`은 둘 다 UBR 큐비입니다. `BN`은 3-cycle이 아니므로 케이스가 없습니다.
같은 큐비 조합은 전부 무효입니다.

### 4.3 378 = 42 × 9

- 버퍼 제외 큐비 7개 → 순서 있는 큐비쌍 7×6 = **42가지 큐비 사이클**
- 각 사이클마다 방향 조합 3×3 = **9가지**
- 42 × 9 = **378**

세 번째 조각의 방향은 강제됩니다(코너 twist 합 ≡ 0 mod 3). 그래서 27이 아니라 9입니다.

### 4.4 같은 큐비쌍의 9개 케이스는 서로 다른 알고리즘이다

예: `BC`, `BM`, `BJ`는 둘째 타깃이 모두 UFR 큐비지만 방향만 다릅니다.
**하나에서 나머지를 유도하는 공식은 없습니다.** 단일 코너를 제자리에서 회전시키는 것이
큐브 법칙상 불가능하기 때문입니다.

다만 insert 면이나 interchange 종류가 규칙적으로 바뀌는 경향은 있어서, 하나를 알면
나머지 유추가 쉬워집니다. UI에서 **같은 큐비쌍의 9개를 묶어 보여주면 학습에 도움**이 됩니다.

### 4.5 역 트릭 — 학습량 절반

`XY`의 알고리즘을 뒤집으면 정확히 `YX`가 됩니다 (378/378 검증됨).

**뒤집기 = 순서 거꾸로 + 각 무브 토글.** 둘 다 해야 합니다.
`2`가 붙은 무브는 토글해도 그대로입니다.

주의: `B' D2 B` 같은 형태는 **뒤집어도 자기 자신**입니다(self-inverse).
양끝이 순서 뒤집기와 토글로 상쇄되고 가운데 `D2`는 자기역원이기 때문입니다.
사용자가 이 부분을 버그로 오해한 적이 있으니, UI에서 A'/B' 파트를 표시할 때
"왜 A와 A'가 같아 보이는지" 혼란이 없도록 주의하세요.

### 4.6 패리티 — OP를 완전히 버릴 수 없다

M2 엣지 + 3-style 코너 조합에서:
- M2도 3-style 커뮤테이터도 순열 패리티가 **EVEN**
- 따라서 둘만으로는 **ODD 순열을 절대 못 품**
- 코너 letter가 홀수면 마지막 1개를 **OP Y-perm으로 1발** 처리해야 함

이유: 패리티 알고리즘(`D' L2 D M2 D' L2 D`)이 엣지에 `UB↔UL` 부작용을 남기는데,
3-style 커뮤테이터는 엣지를 안 건드리므로 아무도 이걸 치워주지 않습니다.
Y-perm이 `UB↔UL`을 한 번 더 만들어 상쇄시킵니다.

**즉 3-style을 다 외워도 OP 코너 표는 계속 필요합니다.** 나중에 관련 안내 페이지를
넣을 때 이 점을 정확히 반영하세요.

### 4.7 break-in은 3-style로 가도 사라지지 않는다

대화 중 한 번 잘못 안내했다가 정정한 내용입니다.

사이클 구조는 **스크램블의 성질**이지 메서드의 성질이 아닙니다. 메모 letter 시퀀스는
OP든 3-style이든 **완전히 동일**합니다. break-in 횟수도 같습니다.

3-style이 다른 점은 letter를 **두 개씩 묶어 실행**한다는 것뿐입니다.
break-in이 페어에 흡수되어 별도 동작이 필요 없어질 뿐, 메모 단계의 사이클 추적 부담은
그대로입니다.

### 4.8 4-style은 존재할 수 없다

사용자가 물어본 내용입니다. 참고로 적어둡니다.

코너 순열 패리티와 엣지 순열 패리티는 **항상 같습니다**(큐브 구조 법칙).
4-cycle은 ODD인데, 엣지를 안 건드리려면 엣지 패리티가 EVEN이어야 하고,
그러면 코너도 EVEN이어야 합니다. 모순입니다.

5-style은 EVEN이라 가능하지만 케이스가 68,040개입니다.

## 5. 앞으로의 확장 순서 (사용자 예상 경로)

1. **지금**: 코너 3-style UBL 조회 앱 (이번 작업)
2. 학습 진도 표시, 랜덤 퀴즈
3. UFR 버퍼 데이터 추가 (이미 생성 완료, 같은 스키마)

5. M2 엣지 / OP 코너 참조표 (기존 PDF 자료 있음)
6. 패리티 안내 페이지
7. 타이머 (멀티페이즈 — csTimer의 아쉬운 점을 개선)
8. 3D 큐브 애니메이션

**데이터 로더를 `buffer` + `pieceType` 키로 분리**해두면 3~5단계 추가가 쉽습니다.
지금은 corner/UBL 하나만 구현하되 구조는 열어두세요.

PDF에서 사용한 UI 관례 중 앱에 이어갈 만한 것:
- 케이스 코드는 가운데 정렬, 알고리즘은 **왼쪽 정렬** (사용자가 명시적으로 요청함 —
  알고리즘이 가운데 정렬되면 읽기 헷갈림)
- `A · B · A' · B'` 경계를 `·` 기호로 구분
- 기준별 정렬 시 **담당 케이스 많은 순** (LB 100 → TU 83 → SC 60 → ...)
- 셋업 짧은 것부터 표시 (쉬운 것 먼저)

## 7. 작업 시 유의사항

- **데이터를 재계산하지 마세요.** `3style_ubl_data.json`을 그대로 쓰세요.
  알고리즘 검증에는 큐브 시뮬레이터가 필요하고, 이미 378/378 통과한 상태입니다.
- **프라임 기호(`'`)를 타이포그래피 따옴표로 변환하지 마세요.** 반드시 ASCII.
  마크다운 렌더러, CSS `font-feature-settings`, 스마트 쿼트 자동변환 모두 주의.
- 큐브 표기는 **고정폭 글꼴** 필수. `R`과 `R'`이 명확히 구분돼야 합니다.
- 사용자는 한국어와 영어 모두 편합니다. UI 언어는 한국어를 기본으로 하되,
  큐브 표기(`R U R' U'`)와 케이스 코드는 영문 그대로 두세요.
- 모바일에서 **연습 중에 한 손으로** 조회하는 상황이 주 사용 시나리오입니다.
  입력이 빠르고 결과가 즉시 나와야 합니다.
