# corner-UBL.json 변경 이력 (schemaVersion 2 → 7)

이 문서는 v3부터 v7까지 **누적**된 변경 기록입니다. 최신은 **v7**이며,
아래 절들은 시간순입니다. 현재 상태만 알고 싶으면 맨 아래 v7 절을 보세요.

## 무엇이 바뀌나

**데이터만 교체. 코드 변경 불필요.** 기존 스키마의 모든 필드가 그대로 유지됩니다.

| | v2 (현재) | v3 (신규) |
|---|---|---|
| 케이스 수 | 378 | 378 (동일) |
| **anchor 수** | **10개** | **6개** |
| anchor 목록 | LB TU SC NG UN WM NU KD UB KS | **GC TC BU IV KS KG** |
| setup 평균 | 11.25수 | 11.19수 |
| **직접 처리 케이스** | **6개** (CU CW UC UW WC WU) | **0개** |
| direct | 변동 없음 | 변동 없음 |

`direct` 쪽은 알고리즘·strict·A/B 파트 모두 **완전히 동일**합니다. 바뀐 건 `setup` 계열뿐입니다.

## 왜 바꾸나

v2의 anchor 중 `UN`과 `NU`가 **서로 역이고 알고리즘이 문자 단위로 동일**했습니다:

```
UN = U R U' L2 U R' U' L2
NU = L2 U R U' L2 U R' U'   ← invert(UN) 과 완전 동일
```

anchor 선정(greedy set-cover)에 **역트릭 경유 경로**를 추가하니 10개 → 6개로 줄었습니다.
평균 길이는 오히려 미세하게 감소(11.25 → 11.19수). 외울 기준공식이 4개 줄어드는 순수 이득입니다.

**상위 2개(GC 164개 + TC 106개)만으로 270/378 커버.**

### 직접 처리 케이스 제거

v2에는 어느 기준으로도 안 닿아 전용 알고리즘을 쓰던 6케이스(`CU CW UC UW WC WU`)가
있었습니다. v3에서는 이들도 **기존 anchor + 3수 셋업**으로 도출됩니다 (무브 수는 13수로 동일).

따라서 **`setup.anchor`가 `"(직접)"`인 케이스는 이제 존재하지 않습니다.**
관련 예외 처리 코드가 있다면 제거해도 됩니다. (남겨둬도 무해)

셋업 길이 분포: 0수 6개 / 1수 54개 / 2수 312개 / 3수 6개

## 새로 추가된 필드

### `cases[].setup.usesInverse` (boolean)

`true`면 "역 케이스를 기준으로 풀고 전체를 뒤집은 것". 378개 중 **186개**가 해당.

**중요**: `setup.alg`에는 **뒤집기와 무브 상쇄가 모두 적용된 최종 실행형**이 들어 있습니다.
앱은 지금처럼 `setup.alg`를 그대로 표시하면 됩니다. 사용자가 실행 중에 뒤집기를 계산할 일 없음.

이 플래그는 **구조 설명용**입니다. 학습 화면에서 "이건 `YX`를 풀고 뒤집은 것"이라고
알려주면 이해에 도움이 됩니다. UI에 안 써도 무방합니다.

### `setup.strict.alg`의 표현

`usesInverse: true`인 경우 strict 형태는 **`S · anchor⁻¹ · S'`**로 표시됩니다.
즉 같은 기준공식을 거꾸로 돌리는 구조. `cancel(strict.alg) === alg`는 여전히 378/378 성립합니다.

### `meta` 추가 필드

- `schemaVersion: 3`
- `anchorCount: 6`
- `anchorLearnOrder`: `["GC","TC","BU","IV","KS","KG"]` — 담당 케이스 많은 순.
  기준 목록을 정렬할 때 이 배열 순서를 그대로 쓰면 됩니다.
- `anchorNote`: fold 경위 설명
- `avgMoves`: `{ direct: 9.02, setup: 11.19 }`

## 앱 코드에서 확인할 것

anchor 키를 **하드코딩한 곳이 있으면** 수정 필요합니다:

- `"LB"`, `"TU"`, `"SC"` 등 v2 anchor 이름을 문자열로 참조하는 코드
- anchor 개수를 10으로 가정한 UI (그리드 레이아웃 등)
- "상위 3개로 243개 커버" 같은 안내 문구 → **"상위 2개로 270개"**로 갱신
- `anchor === "(직접)"` 분기 (이제 해당 케이스 없음)

`Object.keys(data.anchors)`나 `meta.anchorLearnOrder`로 동적 처리하고 있다면 **수정 불필요**합니다.

## 검증

`corner-UBL.json` 기준 **1512/1512 통과**:

1. 각 알고리즘이 해당 케이스를 실제로 푸는가 (direct + setup)
2. 엣지 무영향인가

## v4 추가 수정 — 분류 정합성 (MECE)

v3에는 **anchor 이름과 실제 담당이 어긋나는** 문제가 있었습니다.

예: `KG`라는 이름의 기준공식이 정작 케이스 `KG`를 담당하지 않고 `PW`/`WP`만 맡고,
케이스 `KG`는 `GC` 기준으로 배정되어 있었습니다. 이름이 거짓말을 하는 상태였습니다.
6개 중 3개(`BU`, `KS`, `KG`)가 이랬습니다.

원인은 greedy set-cover가 "누가 몇 개를 덮는가"만 보고 이름과의 정합성은 안 봤기 때문입니다.

### 수정 내용

각 anchor가 **자신의 이름에 해당하는 케이스 쌍을 반드시 직접 담당**하도록 강제했습니다.
anchor `XY`는 케이스 `XY`(셋업 없음)와 `YX`(셋업 없음 + 역트릭)를 항상 소유합니다.

부수 효과로 평균 길이도 11.19 → **11.15수**로 미세하게 개선됐습니다.

### 보장되는 성질 (`meta.partitionNote`)

1. 모든 케이스는 **정확히 하나**의 anchor에 속함 (상호배타)
2. **378/378** 전부 배정 (완결)
3. 역쌍 `XY`/`YX`는 **항상 같은 anchor** (0건 위반)
4. anchor 이름 `XY`는 **자신의 케이스를 직접 담당** (셋업 없음)

### 새 필드

- `cases[].setup.isAnchorCase` (boolean) — 셋업 없이 기준공식 그대로 쓰는 케이스.
  12개(= anchor 6개 × 2)가 해당. UI에서 "이건 기준공식 그 자체"로 표시하면 학습에 도움됩니다.
- `anchors[].ownCases` — 그 anchor가 직접 담당하는 케이스 쌍. 예: `["GC", "CG"]`

### anchor 담당 (v4)

| anchor | 담당 | 자기 케이스 |
|---|---|---|
| GC | 160 | GC, CG |
| TC | 104 | TC, CT |
| BU | 64 | BU, UB |
| IV | 28 | IV, VI |
| KS | 18 | KS, SK |
| KG | 4 | KG, GK |

상위 2개(GC+TC)로 **264/378** 커버.

## v5 — 배정 기준 통일 및 anchor 재선정

v4까지는 **배정 원칙이 혼재**되어 있었습니다. 사용자 지적대로, 기준을 잡았으면
그 안에서는 동일 기준으로 정리되어야 하는데 그렇지 않았습니다.

### 문제 1 — greedy 순서에 따른 우연한 배정

anchor를 순차 선택하면서 **그 시점에 덮인 케이스를 즉시 확정**해버려, 나중에 선택된
anchor가 더 짧은 경로를 제공해도 재검토되지 않았습니다.

단일 기준(가장 짧은 알고리즘)으로 전면 재배정한 결과 **238/378(63%)의 소속이 바뀌었고**,
평균이 **11.15 → 10.43수**로 줄었습니다. 그만큼 기존 배정이 자의적이었습니다.

### 문제 2 — anchor 선정 기준 자체가 틀렸음

anchor를 "커버리지 최대화"로 뽑았는데, 측정해보니 **anchor 1개만으로도 거의 모든
케이스에 도달 가능**했습니다 (셋업 0~3수 허용 시):

| anchor | 단독 도달 |
|---|---|
| GC, TC | 378/378 |
| KG | 376 |
| BU, KS | 370 |
| IV | 364 |

즉 **커버리지는 애초에 제약이 아니었고**, anchor를 늘리는 목적은 알고리즘 단축입니다.
"상위 N개로 몇 개 커버" 같은 프레이밍은 폐기했습니다.

그 결과 **GC는 평균 길이를 전혀 줄이지 못하는 잉여**로 판명되어 제거했습니다
(10.429수 → 10.429수, 변화 없음). **anchor 6개 → 5개.**

### v5 확정 사항

**기준 5개**: `KG` `IV` `BU` `TC` `KS` (학습 순서 = 평균 길이 감소폭 순)

**배정 규칙** (`meta.assignmentRule`) — 전 케이스 예외 없이 동일 적용:
> 5개 기준 중 가장 짧은 알고리즘을 주는 기준에 배정.
> 동률은 손가락 페널티 → 셋업 길이 → 학습 순서로 결정.

**보장 성질** (`meta.partitionNote`):
1. 모든 케이스가 정확히 하나의 기준에 속함
2. 378/378 배정
3. 역쌍 `XY`/`YX`는 항상 같은 기준
4. 기준 이름 `XY`는 자기 케이스 `XY`·`YX`를 셋업 없이 직접 담당

**담당 분포**: KG 112 / IV 100 / KS 62 / TC 54 / BU 50 — v4의 극단적 편중(160/104/64/28/18/4)이
해소되었습니다. 편중은 greedy 순서의 부산물이었습니다.

### 새 필드

- `meta.learningCurve` — 기준을 하나씩 추가할 때의 평균 길이 변화.
  `[KG 11.91(미도달 2), +IV 11.22, +BU 10.85, +TC 10.58, +KS 10.43]`
  **1개만 배워도 거의 다 풀 수 있고, 추가는 단축을 위한 것**임을 UI에 드러내세요.
- `meta.coverageNote`, `meta.assignmentRule`, `meta.partitionNote`
- `anchors[].soloReach` / `soloAvgMoves` — 그 기준 단독으로 도달 가능한 케이스 수와 평균
- `anchors[].ownCases` — 자기 케이스 쌍

### 동봉 파일: `corner-UBL-alternatives.json` (174KB, 선택)

케이스마다 **5개 기준 각각의 경로**를 담았습니다.

배정은 "가장 짧은 것" 하나만 고르지만, 사용자가 아직 `KG`밖에 모른다면 `IV`에 배정된
케이스도 `KG` 경로로 풀 수 있어야 합니다. 이 파일이 그걸 지원합니다.

```jsonc
{ "cases": { "BG": { "KG": {"moves":11,"S":"...","inv":false,"alg":"..."},
                     "IV": {...} } } }
```

학습 진도(아는 기준 목록)와 연동해 **"당신이 아는 기준으로는 이렇게"**를 보여주면
초기 학습자에게 훨씬 실용적입니다. 필요 없으면 번들에서 빼도 됩니다.

## v6 — `cancels` 필드 버그 수정

### 버그

`cancels`를 `(strict.moves - alg.moves) / 2`로 계산했습니다. **상쇄가 항상 무브 2개를
지운다고 가정한 것인데 틀렸습니다.** `R R → R2`는 토큰이 1개만 줄어듭니다.

**378케이스 × 2모드 중 470건이 잘못된 값**이었습니다. 예: `CW`는 실제 1 감소인데 `0`,
`DJ`는 실제 3 감소인데 `1`.

### 수정

`cancels = strict.moves - alg.moves` (줄어든 무브 수). 나눗셈 제거.

### 새 필드 — 화면 표시 혼란 방지

**셋업 길이와 최종 무브 수가 안 맞아 보이는 것은 정상입니다.**

```
총 수 = |S| + anchor(8) + |S| − 상쇄
```

화면의 "10수"는 **상쇄가 끝난 최종 알고리즘** 길이라, 셋업만 보고 역산할 수 없습니다.

- `CP`: S 3수 → 3+8+3=14, 상쇄 6 → **8수**
- `DL`: S 1수 → 1+8+1=10, 상쇄 0 → **10수**

이걸 UI에서 설명할 수 있도록 두 필드를 추가했습니다:

- `setup.setupMoves` — 셋업 무브 수 (정수)
- `setup.breakdown` — 계산 과정 문자열. 예: `"3+8+3=14 → 상쇄 3 → 11"`

### 앱 쪽 권장 사항

셋업(S)과 최종 무브 수를 나란히 보여주면 사용자가 계속 혼란스러워합니다. 셋 중 하나를 하세요:

1. **최종 알고리즘을 항상 함께 표시** (가장 권장) — 그러면 무브 수가 자명해짐
2. `breakdown` 문자열을 툴팁이나 보조 텍스트로 노출
3. 목록 화면에서는 무브 수만 보여주고 셋업은 상세 화면에서만

현재 스크린샷처럼 **"셋업 + 무브수"만 나열하는 형태가 가장 오해를 부릅니다.**

## 문서 정정 및 필드 의미 명확화

앱 통합 과정에서 지적된 사항들을 반영합니다. **데이터는 변경 없음(v7 그대로).**

### 정정 1 — 문서 제목

`schemaVersion 2 → 4`로 되어 있던 제목을 `2 → 7`로 고쳤습니다. 이 문서는 v3부터 누적된
이력이며 중간 버전에서 제목을 갱신하지 않은 실수였습니다.

### 정정 2 — v7 기준공식 계보

v7 절에서 "v6 기준(GC TC BU IV KS KG)"이라 적었으나 **그건 v3~v4의 6개 목록**입니다.
v6은 `KG IV BU TC KS` 5개였습니다. 따라서:

- v6 → v7에서 **살아남은 것은 `BU` 하나뿐**
- `GC`는 v5에서 제거됐다가 v7에서 **복귀**한 것이지 유지된 것이 아님

### `anchorLearnOrder` 의 의미 — 담당 수 순이 아님

```
anchorLearnOrder: GC BU DO CH IT OI SC VJ SV TH
담당 수:          44 38 28 28 42 38 44 38 40 38
```

이건 **한계 이득 순서**입니다. 각 단계에서 "다음에 무엇을 추가해야 평균 무브가 가장 많이
줄어드는가"로 greedy 선택한 결과이며, `meta.learningCurve`가 이 순서와 짝을 이룹니다:

```
1개 12.19 → 2개 11.44 → 3개 10.98 → … → 10개 9.94
```

**담당 수 순으로 정렬하면 안 됩니다.** 담당 수는 "최종 10개 체제에서 그 기준이 몇 케이스를
맡는가"이고, 학습 순서는 "몇 개까지 알 때 얼마나 좋아지는가"라 축이 다릅니다.

`learningCurve[i].anchors` 에 해당 단계의 기준 목록이 명시돼 있으니, 순서를 바꿀 일이 있으면
그쪽도 함께 봐야 합니다.

> v5 때 "학습 순서 = 담당 많은 순"이라는 단언을 걷어낸 것이 여기서도 유효합니다.
> 커버리지가 제약이 아니게 된 시점부터 담당 수와 학습 우선순위는 분리됐습니다.

### `strict.cancelNote` 제거

v6에서 추가했던 설명 문자열이 v7 생성 시 누락됐습니다. **코드가 읽지 않는 필드이므로
무해**하며, 같은 내용이 `meta.strictNote` 에 있습니다. 복구하지 않습니다.

필요하면 데이터 동일한 v8 패치로 되돌릴 수 있으나, 통합이 끝난 상태에서 문자열 하나를 위해
버전을 올릴 이유는 없다고 판단했습니다.

### 테스트 작성 시 주의 (앱 쪽 교훈)

v7에서 **`sameAlg: true` 인 케이스가 105개**입니다. `direct.alg` 와 `setup.alg` 가 같은
무브 열로 떨어지는 경우이며, 버전마다 어느 케이스가 여기 해당하는지 달라집니다.

- "두 경로가 서로 다른 무브 열"을 검증하려면 `sameAlg === false` 인 것 중에서 고를 것 (273개)
- 기준 이름(`IV` 등)을 테스트에 하드코딩하면 기준 세트가 바뀔 때 깨짐.
  `meta.anchorLearnOrder[0]` 이나 `Object.keys(anchors)` 로 데이터에서 고를 것

## v8 — learningCurve 목적함수 불일치 수정 (버그)

앱 통합 검증에서 발견된 **데이터 버그**입니다. 지적 내용이 원인까지 정확했습니다.

### 증상

같은 "기준 10개 전부" 상태의 평균이 데이터 안에 두 값으로 존재했습니다.

```
meta.avgMoves.setup            = 10.05   (실제 배정과 일치)
meta.learningCurve[9].avgMoves =  9.94   (과소)
```

### 원인

`learningCurve` 를 계산할 때 케이스별 최소를 **무브 수만으로** 취했습니다.
실제 배정은 v7 목적함수 `(셋업길이 → 무브수 → 손가락점수 → 기준순서)` 를 따르므로,
**34개 케이스에서 더 짧은 알고리즘 대신 셋업이 짧은 쪽을 택합니다.** 그 차이 합계 44수,
378로 나누면 0.1164수 — 보고된 차이와 정확히 일치합니다.

즉 v7까지의 곡선은 "무브만 최소화했다면 얼마였을까"라는 **도달 불가능한 낙관값**이었습니다.

### 영향 범위 조사 — `anchorLearnOrder` 는 무사

같은 오염이 기준 선정에도 있었는지 재탐색했습니다. **없었습니다.**

| 선정 목적함수 | 결과 순서 |
|---|---|
| **v7 (셋업길이→무브)** | `GC BU DO CH IT OI SC VJ SV TH` — **현재와 완전 일치** |
| 무브 최소 전용 | `TL VJ OP SC TP IV KG BU DK CO` — 전혀 다른 집합 |

기준 선정 greedy 는 처음부터 v7 목적함수를 썼고, 오염은 **곡선 계산 단계에서만** 발생했습니다.
따라서 앱이 노출하는 학습 순서는 실제 체감 이득 순서와 어긋나지 않습니다.

### 수정

`learningCurve` 를 **실제 v7 배정 절차 그대로**(namesake 강제·역쌍 통일 포함) 재계산했습니다.

| k | 구(무브전용) | 신(v7배정) |
|---|---|---|
| 1 | 12.19 | 12.19 |
| 2 | 11.44 | 11.47 |
| 3 | 10.98 | 11.03 |
| 4 | 10.76 | 10.88 |
| 5 | 10.50 | 10.63 |
| 6 | 10.40 | 10.50 |
| 7 | 10.28 | 10.39 |
| 8 | 10.11 | 10.21 |
| 9 | 10.01 | 10.13 |
| **10** | 9.94 | **10.05** |

**`learningCurve[9].avgMoves === meta.avgMoves.setup === 10.05`** 이 이제 보장됩니다.

### 곡선 항목 확장

각 지점이 자기 기준을 스스로 설명하도록 필드를 추가했습니다.

```jsonc
{
  "anchors": ["GC","BU", ...],
  "avgMoves": 10.05,
  "avgSetupMoves": 1.42,          // 신규
  "setupLengthDist": {"0":20,"1":186,"2":166,"3":6},  // 신규
  "unreachable": 0
}
```

`avgSetupMoves` 와 `setupLengthDist` 로 **셋업 길이 관점의 학습 곡선**도 그릴 수 있습니다.
v7 목적함수의 1순위가 셋업 길이이므로, 체감 이득은 오히려 이쪽이 더 잘 반영합니다.

### 새 meta 필드

- `meta.learningCurveNote` — 곡선의 계산 기준 명시 및 v7 버그 이력
- `meta.anchorLearnOrderNote` — 한계 이득 순서이며 담당 수 순이 아님을 명시 (재정렬 금지)

### 앱 쪽 대응

**두 값 중 어느 쪽을 노출할지 고민할 필요가 없어졌습니다.** 이제 같은 기준이므로:

- 현재 상태 평균 → `meta.avgMoves.setup` 또는 `learningCurve[마지막].avgMoves` (동일 값)
- 학습 진도별 예상 평균 → `learningCurve[k-1]`

데이터 외 변경 없음. 알고리즘·배정·기준 세트는 v7과 완전히 동일합니다.

## v8 — learningCurve 목적함수 불일치 수정

**버그가 맞습니다.** 지적대로 `learningCurve` 와 실제 배정이 서로 다른 목적함수로 계산돼
있었습니다.

### 원인

| | 사용한 목적함수 |
|---|---|
| 실제 배정 (`cases[].setup`) | 셋업길이 → 무브수 → 손가락점수 → 기준순서 |
| `meta.learningCurve` (v7까지) | **무브수만** |

생성 스크립트에서 곡선을 계산할 때 `min(moves)` 만 취해, 셋업 길이를 우선하는 실제 배정
규칙을 반영하지 못했습니다. 그 결과 곡선이 **실제보다 낙관적**이었습니다.

34개 케이스에서 "더 짧은 알고리즘"과 "더 짧은 셋업"이 갈리며, 합계 44수 = 평균 0.1164 차이.

### 질문 2 — `anchorLearnOrder` 는 영향 없음 (검증 완료)

곡선과 달리 **기준 선정 greedy 는 처음부터 v7 목적함수를 썼습니다.** 각 단계에서
`(미커버, 평균셋업길이, 평균무브)` 로 다음 기준을 골랐습니다.

v7 목적함수로 순서를 재계산해 대조한 결과 **완전히 동일**합니다:

```

저장값: GC BU DO CH IT OI SC VJ SV TH   → 일치
```

따라서 앱이 노출하는 학습 순서는 체감 이득 순서와 어긋나지 않습니다. 순서는 그대로 두고
곡선 값만 고쳤습니다.

### 새 필드

- `learningCurve[].avgSetupMoves` — 해당 단계의 평균 셋업 길이.
  2.51 → 1.42 로 줄어드는 것이 기준을 늘리는 주된 이득임을 보여줍니다
- `meta.learningCurveNote` — 계산 기준 명시

### 변경 범위

`meta.learningCurve`, `meta.learningCurveNote`, `meta.schemaVersion` **셋뿐**입니다.
378케이스 알고리즘·배정·기준공식·`anchorLearnOrder` 모두 v7과 **바이트 단위로 동일**합니다.

앱 쪽은 `avgMoves.setup` 과 `learningCurve[9].avgMoves` 중 어느 쪽을 노출해도 이제 같은 값입니다.

## v9 — 시뮬레이터 L 면 정의 오류 수정 (중대)

**생성에 쓰인 시뮬레이터의 `L` 정의가 표준의 역이었습니다.**

```
표준 L : U → F → D → B   (U 스티커가 F 로)
버그 L : U → B → D → F   (D 스티커가 F 로)   ← 즉 물리적 L'
```

나머지 `U D R F B` 와 회전 `x y z` 는 전부 표준과 일치했습니다. **오직 `L` 만** 뒤집혀
있었고, 코너·엣지 양쪽에서 일관되게 뒤집혀 있어 내부적으로는 유효한 큐브 모델이었습니다.
그래서 자체 검증을 전부 통과했습니다.

### 왜 여태 못 잡았나

수행했던 검증이 모두 **순환 논증**이었습니다.

- `x = R L'`, `y = U D'`, `z = F B'` → 시뮬레이터 **내부 정의끼리** 비교라 전역 뒤집힘을 못 잡음
- T-perm, sexy move, 합성 순서 검증 → **`L` 을 쓰지 않는** 알고리즘
- 378 전수 검증 → 같은 도구로 만들고 같은 도구로 확인

**실제 큐브로 돌려본 것이 유일하게 유효한 외부 검증이었고, 그래서 발견됐습니다.**

### 수정 내용

1. 시뮬레이터 `L` 정의 교정 → 6면 4-cycle 전부 표준과 대조 확인
2. 모든 알고리즘 문자열에서 `L ↔ L'` 교환 (`L2` 는 영향 없음)
3. **`cube_perms.json` 재생성** — 앱에 배포된 이 파일에도 같은 버그가 있었음.
   퀴즈 채점 등에 사용했다면 그동안 오답 처리되었을 수 있음

### 영향 범위

| | 개수 |
|---|---|
| `L` 또는 `L'` 포함 → **값 변경** | **320 / 756** (42%) |
| `L2` 만 포함 → 불변 | 152 |
| `L` 계열 없음 → 불변 | 284 |

**기준공식 10개 중 5개 변경** (`DO` `CH` `IT` `OI` `SV`).
`BU` `VJ` 는 `L2` 만 써서 불변, 나머지 3개는 `L` 미사용.

케이스 배정·기준 선정·무브 수·MECE 성질·`learningCurve` 는 **전부 불변**입니다. 표기만 교정됐습니다.

### 외부 라이브러리 교차 검증 (신규)

자체 시뮬레이터를 신뢰할 수 없으므로 **독립 라이브러리 `cubejs`** (Kociemba 2-phase 구현,
npm 표준 패키지) 로 전수 재검증했습니다.

- 큐비 단위: **756 / 756 통과**
- 스티커 단위(방향 포함): **756 / 756 통과**
- `cubejs` 의 6면 정의가 표준과 일치함을 먼저 확인 후 진행

검증 스크립트를 `xcheck-cubejs.mjs` 로 동봉합니다. `npm i cubejs` 후 `node xcheck-cubejs.mjs`.

**앞으로 이 프로젝트의 알고리즘 검증은 `cubejs` 를 기준으로 합니다.** 자체 시뮬레이터는
탐색 성능을 위해 유지하되, 최종 산출물은 반드시 외부 라이브러리로 교차 확인합니다.
